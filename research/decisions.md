## สรุป

TMS ของเราขายแบบ SaaS ให้บริษัทขนส่งทางบก 10–200 คัน สมัครใช้เองได้ มี Platform Console ให้ทีมเราจัดการ (HANDOFF §1) ข้อตกลงที่ตัดสินแล้วและห้ามย้อน (HANDOFF §2) คือ standalone ครบเป็นค่าเริ่มต้น, ไม่ผูกสัญญายาว, และฟีเจอร์พื้นฐาน (ePOD, วางบิล, เอกสารภาษี) ต้องอยู่ทุกแพ็กเกจ งาน A–C ค้นตลาดไทยเสร็จแล้วและพบว่า (1) ไม่มีมาตรฐานหน่วยคิดเงินในตลาด TMS ไทย แต่ลูกค้าชินจ่าย GPS ต่อคัน ~200–375 บาท/เดือน (2) กรมสรรพากรมี SOAP API สาธารณะให้ตรวจเลข 13 หลักและ prefill ได้ ส่วน DBD ไม่มี API ที่พึ่งได้ใน production (3) Opn เป็น gateway ที่ครบและเปิดราคาที่สุด เหลือ 5 คำถามที่ต้องให้ผู้บริหารเคาะ เพราะกระทบ data model (`UsageRecord`, `Tenant.status`, `PlanVersion`) ที่ต้อง freeze ก่อนเขียนโค้ดเฟส 0 เอกสารนี้ให้ตัวเลือก หลักฐาน และคำแนะนำ 1 ข้อต่อคำถาม

| # | คำตัดสินใจที่ต้องการ | คำแนะนำ | ความเร่งด่วน | ใครตัดสิน |
|---|---|---|---|---|
| 1 | หน่วยคิดเงิน | **ต่อรถ active/เดือน** รวมรถร่วม นิยามจากเอกสารที่ปิดงาน | ก่อน freeze schema เฟส 0 | Wei (เจ้าของสินค้า) |
| 2 | สมัครแล้วใช้ได้ทันทีหรือรออนุมัติ | **Hybrid**: ใช้ trial ได้ทันที + ตรวจอัตโนมัติด้วย RD API + คิวอนุมัติเฉพาะเคสไม่ผ่าน | ก่อน freeze schema เฟส 0 (สถานะ tenant) | Wei + ฝ่ายกฎหมาย (Privacy Notice) |
| 3 | Payment gateway + รับโอน/สลิป | **Opn หลัก** + EasySlip สำหรับสลิป, ออกใบกำกับภาษีเองเป็น PDF เฟส 1, e-Tax ผ่าน SP เฟส 2 | สมัคร Opn ปลายเฟส 0 (รออนุมัติ 15 วันทำการ) | Wei + นักบัญชีของเรา |
| 4 | ราคาและโควตา | **249 / 399 / 499 บาท/รถ active/เดือน** (เพิ่มตามฟีเจอร์) + ส่วนลดปริมาณ 51–100 คัน −10%, 101+ −20% | ก่อนเปิดหน้าราคาเฟส 1; โครง `PlanVersion` ต้องมีเฟส 0 | Wei |
| 5 | Grace period + เก็บข้อมูลหลังยกเลิก | past_due 7 วัน → read-only ถึงวันที่ 21 → suspended ถึงวันที่ 60 → cancelled; เก็บข้อมูล 90 วัน; เอกสารภาษีที่เราออก ≥ 5 ปี (กฎหมาย) เสนอ 7 ปี | ก่อน freeze state machine เฟส 0 (ทำเป็น config) | Wei + นักบัญชี + ฝ่ายกฎหมาย |

## 1. หน่วยคิดเงิน: ต่อรถ active / ต่อเที่ยว / ต่อ user

**บริบท:** one-platform §2.2 และ v2 §2 เสนอ "ต่อรถ active" ไว้แล้วแต่ยังไม่ได้เคาะ และนิยาม "active" ยังต่างกันเล็กน้อย (v2: มี Trip ≥ 1; pricing-th §8: มีงานปิดสถานะ ≥ 1) ต้องเคาะนิยามเดียวเพราะเป็นสิ่งที่ `UsageRecord` นับและเป็นข้อความบนหน้าราคา

| ตัวเลือก | ข้อดี | ข้อเสีย | ผลต่อ product | ผลต่อ dev |
|---|---|---|---|---|
| **A. ต่อรถ active/เดือน** (แนะนำ) | ลูกค้าขนส่ง "นับรถเป็น" และจ่าย GPS ต่อคันอยู่แล้ว (pricing-th §2 FACT: CHY 200, Cartrack 299, CPIB 375/คัน/เดือน); รถที่ไม่วิ่งไม่เสียเงิน → จุดขายเหนือ GPS; เปิด user ไม่จำกัดได้ (ตาม Alvys/Onfleet FACT one-platform §1, pricing-th §6) | ต้องนิยาม active ให้ชัดและกันเลี่ยง (ยุบหลายคันลงทะเบียนเดียว — pricing-th §8.3 OPINION); รายได้ผันผวนตามฤดูกาลขนส่ง | หน้าราคาเทียบกับค่า GPS ได้ตรง ๆ; ขั้นต่ำต่อเดือนต้องมีเพื่อกัน fleet 2–3 คัน | ต้องมี `UsageRecord(metric=active_vehicles)` นับจากทะเบียนบน DO/POD ณ สิ้นเดือน + cron ปิดงวด; ความยาก "กลาง" (one-platform §2.8) |
| B. ต่อเที่ยว/ต่องาน | ตรงกับการใช้จริงที่สุด; 360TechX ใช้ (ฟรี ≤100 งาน/เดือน — pricing-th §1.1 FACT); Alvys คิดต่อ load (FACT) | ลูกค้าไทยคาดเดาค่าใช้จ่ายรายเดือนไม่ได้; จูงใจให้ลูกค้าไม่สร้างงานในระบบ (ขัดกับการที่ ePOD/วางบิลต้องเกิดในระบบ); ชนกับ 360TechX ที่ให้ฟรี | ต้องทำ tier ตามช่วงงานหลายขั้น + ค่าเกินโควตา (แบบ Shipday FACT) | นับง่ายกว่า A แต่ต้องมี metering + alert ใกล้โควตา + proration |
| C. ต่อ user | เข้าใจง่าย, ตลาด SaaS ทั่วไปใช้ | ลงโทษการให้ทั้งทีม/คนขับ/รถร่วมเข้าระบบ ซึ่งเป็นจุดที่ TMS ล้มบ่อยสุด (v2 §2 OPINION); ePOD ต่างประเทศคิดต่อ driver $39–99 ≈ 1,300–3,300 บาท แพงกว่าที่รถร่วมไทยรับได้ (pricing-th §3 FACT+OPINION) | ขัดกับหลัก "user ไม่จำกัดทุก tier" ใน v2 | นับง่ายที่สุด แต่ต้องกันแชร์บัญชี |
| D. เหมารายเดือนตามขนาด (Skyfrog 7,500–30,000 FACT) | รายได้คงที่ | ลูกค้า 10 คันกับ 60 คันจ่ายเท่ากันในขั้นเดียว; ต้องมีสัญญาขั้นต่ำเพื่อคุ้ม (Skyfrog ขั้นต่ำ 1 ปี FACT) ซึ่งขัดข้อตกลงข้อ 6 | ต้องแบ่งหลายขั้น ไม่ต่างจาก A แต่โปร่งใสน้อยกว่า | ง่ายที่สุด |

**หลักฐาน:** ตลาด TMS ไทยที่เปิดราคาใช้ 3 หน่วยต่างกัน (ต่อคัน MoveMax/Vcago, ต่อ driver Skyfrog, ต่องาน 360TechX) → ไม่มีมาตรฐาน เราตั้งต่อรถ active ได้โดยไม่ขัดความคาดหวัง (pricing-th §1.2 OPINION อิง FACT ตาราง §1.1) · Dashdoc/OptimoRoute คิดต่อ active จริง (one-platform §1 "เพิ่มจาก research ก่อนหน้า")

**คำแนะนำ: A — ต่อรถ active/เดือน** เพราะเป็นหน่วยที่ลูกค้าเป้าหมายจ่ายอยู่แล้ว (GPS), ทำให้ user ไม่จำกัดได้ตามหลัก v2, และเป็นข้อได้เปรียบเดียวที่เทียบ GPS/MoveMax ได้ตรง

**นิยาม "รถ active" ที่เสนอ (OPINION รวมจาก v2 §2 + pricing-th §8):**
- รถ 1 คัน = ทะเบียนรถ 1 ทะเบียนใน tenant (รถบริษัท **และ** รถร่วม) ที่ปรากฏบน DO/Trip ที่ **ปิดสถานะ** (ส่งสำเร็จ/ปิดงาน/ยกเลิกหลังออกวิ่ง) อย่างน้อย 1 ใบในเดือนปฏิทินนั้น นับ ณ 23:59 วันสิ้นเดือน (เวลาไทย)
- รถที่มีแค่ Trip แบบร่าง/ยังไม่ออกวิ่ง ไม่นับ; ทะเบียนที่ถูกลบกลางเดือนแต่มีงานปิดแล้วยังนับ
- รถร่วมคิดราคาเท่ารถบริษัท (v2 §8 เคยเสนอคิดครึ่ง — เอกสารนี้ **ไม่แนะนำ** เพราะทำให้ลูกค้าย้ายรถไปจดเป็นรถร่วมเพื่อลดบิล; จูงใจรถร่วมด้วยลิงก์ POD ฟรีแทน ตาม v2 §6)
- ขั้นต่ำต่อเดือนตามแพ็กเกจ (ข้อ 4) กัน fleet ต่ำกว่า 10 คัน; เพิ่ม/ลดรถกลางเดือนมีผลเดือนถัดไป (v2 §2)

**สิ่งที่ต้องทำถ้าเลือกตามคำแนะนำ:** (1) เขียนนิยามนี้ลงหน้าราคาและ Terms (2) `UsageRecord` + cron ปิดงวดวันที่ 1 ของเดือน + หน้า "แพ็กเกจของฉัน" แสดงรถ active แบบ real-time (one-platform §2.6) (3) ผูก active กับทะเบียนบน ePOD/ใบส่งของ ไม่ใช่ master รถ (กันเลี่ยง) (4) ทำ unit test ของตัวนับก่อนออกบิลจริง

## 2. สมัครแล้วใช้ได้ทันที หรือรอทีมอนุมัติ

**บริบท:** one-platform §2.4 เสนอ flow 3 ขั้น (OTP มือถือ → ข้อมูลบริษัท + ตรวจเลขนิติบุคคล → เลือกแพ็กเกจ/trial) และตั้งคำถามว่าจะ "อนุมัติอัตโนมัติ" หรือ "ให้ทีมตรวจ" งาน B ตอบแล้วว่าตรวจอัตโนมัติทำได้แค่ไหน

**ผลจากงาน B ที่กระทบคำตอบ:**
- **FACT** กรมสรรพากรมี SOAP Web Service สาธารณะ 2 ตัว (username/password = `anonymous`): TIN Service เช็กว่าเลข 13 หลักมีจริง, VAT Service คืนชื่อ/ที่อยู่แยกฟิลด์/สาขา/วันจด VAT → PEAK ใช้วิธีนี้ prefill ตอนสมัคร (company-verification §2.2)
- **FACT** DBD DataWarehouse+ ไม่มี API ทางการ; `openapi.dbd.go.th` ที่ third-party ใช้ไม่มีเอกสารทางการและโดน WAF 403 ตั้งแต่ ก.ย. 2569; BDEX เป็น API ทางการแต่ต้องสมัคร-อนุมัติ-จ่ายค่าธรรมเนียม (ไม่พบตัวเลข) (company-verification §1)
- **OPINION (งาน B)** ข้อจำกัด: บริษัทที่ไม่จด VAT (รายได้ < 1.8 ล้าน/ปี) จะไม่พบใน VAT Service และ RD ไม่ให้สถานะ "เลิกกิจการ" → ต้องมี manual review เป็น fallback เสมอ (§2.2)
- **ไม่พบข้อมูล** rate limit/SLA ของ RD Web Service และยังไม่ได้ทดสอบจากเครื่องในไทย (§2.2, §8)

| ตัวเลือก | ข้อดี | ข้อเสีย | ผลต่อ product | ผลต่อ dev |
|---|---|---|---|---|
| A. ใช้ได้ทันทีทุกราย ไม่ตรวจ | สมัครสั้นสุด (OptimoRoute 3 ช่อง FACT one-platform §1); conversion สูง | สแปม/บัญชีซ้ำ; ออกใบกำกับภาษีให้เลขปลอมไม่ได้; ไม่รู้ว่าลูกค้าเป็นใครจนจ่ายเงิน | ข้อมูลบริษัทต้องกรอกเองทั้งหมด | ง่ายสุด แต่ต้องทำ KYC ซ้ำตอนจ่ายเงิน |
| B. รอทีมอนุมัติทุกราย | กันทุจริตได้ 100%; ทีมได้คุยกับลูกค้าทุกราย | ลูกค้ารอ 1 วันทำการ+ ขัดกับ "เห็นราคาแล้วกดสมัครได้" ซึ่งเป็นช่องว่างตลาด (pricing-th §1.2 OPINION); ภาระทีมโตตาม sign-up | เหมือน Shipsy/NOSTRA ที่ต้อง "Talk to sales" (FACT one-platform §1) | ต้องมีคิวอนุมัติใน Console ตั้งแต่เฟส 0 |
| **C. Hybrid** (แนะนำ) | ใช้ trial ได้ทันทีถ้า RD ตรวจผ่าน (prefill ชื่อ-ที่อยู่เหมือน PEAK); เฉพาะไม่ผ่าน/API ล่ม/เลขซ้ำ เข้าคิว; ยังใช้ trial ได้แบบจำกัด | พึ่ง RD API ที่ไม่มี SLA ประกาศ → ต้อง circuit breaker; บริษัทไม่จด VAT ต้องอัปโหลดหนังสือรับรอง | ลูกค้าส่วนใหญ่ (จด VAT) เข้าใช้ภายใน 1 นาที; สถานะ tenant มี `pending_verification` | ความยาก "กลาง" (one-platform §2.8); ต้องเขียน SOAP client, cache, คิวอนุมัติ |
| D. ตรวจด้วย Apify/ผู้ให้บริการเอกชน | ได้ TSIC/สถานะ/กรรมการ | Apify เป็น scraper ต่างชาติ $0.025/record (FACT §4) เสี่ยงกฎ DBD + PDPA (§5.1 FACT ประกาศ DBD); Creden/BOL ไม่เปิดราคา | เหมาะเป็น enrichment ไม่ใช่เส้นทางสมัคร | เพิ่ม dependency ภายนอกที่ควบคุมไม่ได้ |

**คำแนะนำ: C — Hybrid ตาม flow ใน company-verification §7.1** คือ checksum ฝั่ง client → dedup `(tax_id, branch_no)` → RD VAT Service prefill (`AUTO_VAT`) → ถ้าไม่พบแต่ TIN มีจริง ให้กรอกเอง + อัปโหลดหนังสือรับรอง (`PENDING_MANUAL`) → DBD openapi เป็น enrichment แบบ async ไม่บล็อก → ทุกเคสไม่ผ่านยังสร้างบัญชี trial ได้ (จำกัด เช่น ≤ 5 คัน, ออกใบกำกับภาษีในระบบไม่ได้จนกว่าจะอนุมัติ) และทีมตรวจกับ DBD DataWarehouse+ ด้วยมือภายใน 1 วันทำการ เหตุผล: ได้ทั้ง conversion ของ A และความปลอดภัยของ B โดยไม่สร้างภาระทีมเกินจำเป็น และ PEAK พิสูจน์แล้วว่าวิธีนี้ใช้ได้กับลูกค้า SME ไทย

**นโยบายที่เสนอใน Console (ตั้งค่าได้ ไม่ hardcode — one-platform §2.4):**

| เคส | ผล |
|---|---|
| checksum ไม่ผ่าน | ปฏิเสธทันทีที่ UI |
| VAT Service พบ + ชื่อที่กรอกตรง | อนุมัติอัตโนมัติ → `trialing` |
| VAT พบ แต่ชื่อไม่ตรง / TIN มีแต่ไม่จด VAT / เลขซ้ำกับ tenant เดิม | `pending_verification` + trial จำกัด + คิวอนุมัติ |
| RD ล่ม (timeout/5xx ติดกัน 5 ครั้ง) | circuit breaker 5 นาที → ทุกเคสเข้า `pending_verification` อัตโนมัติ |
| หลักแรก ≠ 0 (บุคคลธรรมดา) | เส้นทางสมัครแบบบุคคล + Privacy Notice (PDPA ฐานสัญญา — §5.2 OPINION ต้องให้ฝ่ายกฎหมายยืนยัน) |

**สิ่งที่ต้องทำถ้าเลือกตามคำแนะนำ:** (1) ทดสอบ WSDL ของ RD จากเครื่องในไทยก่อนเขียนโค้ด (company-verification §8 ข้อ 1 — sandbox ถูกบล็อก) (2) เพิ่มสถานะ `pending_verification` ใน `Tenant` และ unique index `(tax_id, branch_no)` (3) หน้า "คิวอนุมัติการสมัคร" ใน Platform Console เฟส 0 (one-platform §2.7) (4) ฝ่ายกฎหมายร่าง Privacy Notice ที่ระบุว่าส่งเลขไป RD เพื่อตรวจสอบ (5) Phase 2 สมัคร BDEX เมื่อต้องการสถานะนิติบุคคล/Business Digital ID

## 3. Payment gateway และการรับโอน + แนบสลิป

**บริบท:** ลูกค้าเป็นนิติบุคคลไทย จ่ายรายเดือน/รายปีหลักพัน–หลักหมื่น ต้องการใบกำกับภาษีจากเรา (payment-gateway §0) one-platform §2.6 กำหนดว่าหน้า "แพ็กเกจของฉัน" ต้องรับได้ 3 ทาง: บัตร / PromptPay QR / โอน + แนบสลิป

**ผลจากงาน C (ค่าธรรมเนียมก่อน VAT 7%):**

- **FACT** ม.105 ทวิ: สำเนาใบรับ (ใบเสร็จ) เก็บ ≥ 5 ปี
- **FACT** เก็บเอกสาร VAT นอกสถานประกอบการต้องยื่นคำร้องขออนุญาต (ท.ป.116/2545) → OPINION งาน tax: ถามนักบัญชีว่า cloud storage ต้องแจ้งไหม
- **OPINION (งาน tax)** ห้าม hard-delete เอกสารภาษี; retention ≥ 7 ปี; เก็บ PDF ที่ render ณ วันออก (immutable)
- ข้อนี้ใช้กับ **2 ชุดเอกสารแยกกัน**: (ก) ใบกำกับภาษี/ใบเสร็จที่ **เราออกให้ลูกค้า** (`PlatformInvoice`) — เป็นหน้าที่ของเราโดยตรง (ข) เอกสารภาษีที่ **ลูกค้าออกให้ลูกค้าของเขาในระบบ TMS** — หน้าที่ตามกฎหมายเป็นของลูกค้า แต่ถ้าเราลบก่อนเขา export เขาจะเสียหาย

| ตัวเลือก | ข้อดี | ข้อเสีย | ผลต่อ product/dev |
|---|---|---|---|
| A. เข้ม: past_due 3 วัน → suspend ทันที; ลบข้อมูล 30 วันหลังยกเลิก | เก็บเงินเร็ว; storage ต่ำ | B2B ไทยจ่ายช้าเพราะรอบอนุมัติภายใน (payment-gateway §6.1 OPINION) → ระงับลูกค้าดีโดยไม่จำเป็น; ลูกค้าเสียเอกสารภาษี → ความเสี่ยงชื่อเสียง | ง่าย แต่ support หนัก |
| **B. ขั้นบันได** (แนะนำ) | ให้เวลาจ่ายแต่กดดันเพิ่มทีละขั้น; read-only ยังให้ดู/export ได้ตาม one-platform §2.5 | ลูกค้าบางรายอยู่ read-only ฟรีเพื่อดูข้อมูลเก่า → จำกัดที่ 14 วัน | ต้องมี 4 สถานะ + cron เปลี่ยนสถานะ + banner + อีเมล/LINE; guard ตัวเดียวตรวจ `status` (one-platform §2.3) |
| C. หลวม: grace 30 วัน ไม่ suspend จนครบ 90 วัน | churn ต่ำ | เงินค้างสะสม; ลูกค้าใช้ฟรี 3 เดือนแล้วหาย | ง่าย แต่ cash flow เสีย |

**ตัวเลขที่เสนอ (OPINION ของเอกสารนี้ — ทุกค่าเป็น config ใน `PlatformSetting` ไม่ hardcode):**

| สถานะ | เริ่ม (นับจากวันครบกำหนดชำระ = วัน 0) | ลูกค้าทำอะไรได้ | ระบบทำอะไร |
|---|---|---|---|
| `past_due` | วัน 0–7 | ใช้งานได้ปกติ | banner สีเหลือง; อีเมล/LINE วัน 1, 3, 6; retry บัตร +1/+3/+5 (payment-gateway §6.2) |
| `read_only` | วัน 8–21 | ดู/ค้นหา/export/พิมพ์เอกสารเดิมได้; สร้าง DO/Trip/ใบกำกับใหม่ไม่ได้; หน้าชำระเงินเข้าได้ | banner สีแดง; อีเมลวัน 8, 14, 20; แจ้ง sales ใน Console |
| `suspended` | วัน 22–60 | login ได้เฉพาะหน้าชำระเงิน + ขอ export (ตาม LogisticsX ยกเว้น endpoint `/subscriptions`, `/payments` — FACT one-platform §1) | อีเมลวัน 22, 45, 55 แจ้งว่าจะยกเลิกวัน 61 |
| `cancelled` | วัน 61 (หรือลูกค้าขอยกเลิกเมื่อสิ้นรอบ) | ขอ export ได้ภายในระยะเก็บข้อมูล | ส่งไฟล์ export (เอกสารภาษี PDF + CSV + รูป POD zip) ให้อัตโนมัติในวันยกเลิก |
| จ่ายสำเร็จในสถานะใดก็ได้ก่อนวัน 61 | → `active` ทันที | | ไม่มีค่าปรับ/ค่าเปิดใหม่ (ข้อตกลงข้อ 6) |

**ระยะเก็บข้อมูลหลังยกเลิก (OPINION):**

| ข้อมูล | เก็บ | เหตุผล |
|---|---|---|
| ข้อมูลปฏิบัติการของลูกค้า (DO, Trip, รูป POD, พิกัด, user) | **90 วัน** soft-delete แล้ว purge; ขอต่ออายุ "archive" ได้เป็น add-on | ตรงกับ v2 §4; พอสำหรับลูกค้ากลับมา (reactivate ได้ไม่ต้อง import ใหม่) |
| เอกสารภาษีที่ **ลูกค้าออกในระบบ** (ใบกำกับ/ใบเสร็จ/ใบลดหนี้/50 ทวิ) | **90 วัน** เท่ากัน แต่ **ต้องส่ง export PDF+CSV ให้ก่อน purge** และบันทึกหลักฐานการส่ง | หน้าที่เก็บ 5 ปีเป็นของลูกค้า (ม.87/3) เราทำให้เขาทำหน้าที่ได้; ถ้าเก็บให้ยาวกว่านี้ต้องคิดเป็น add-on และระวังเรื่องสถานที่เก็บ (ท.ป.116/2545) |
| ใบกำกับภาษี/ใบเสร็จที่ **เราออกให้ลูกค้า** (`PlatformInvoice/Payment`) + ข้อมูลผู้ซื้อที่จำเป็น | **≥ 5 ปีตามกฎหมาย เสนอ 7 ปี** ไม่ลบแม้ลูกค้ายกเลิก; เป็น immutable PDF | ม.87/3 + ม.105 ทวิ (FACT); 7 ปีเผื่ออธิบดีขยาย (OPINION งาน tax) |
| Audit log / ImpersonationLog / log การส่งเลข 13 หลักไป RD | 2 ปี (ข้อเสนอ) / raw response RD 90 วัน (company-verification §7.2) | PDPA accountability |
| ข้อมูลส่วนบุคคลคนขับ/ผู้ติดต่อ | purge พร้อมข้อมูลปฏิบัติการ (90 วัน) ยกเว้นที่อยู่บนเอกสารภาษี | v2 §4 "เก็บเท่าที่จำเป็น"; PDPA |

**คำแนะนำ: B** ด้วยตัวเลข 7 / 14 / 39 วัน (รวมถึงวัน 60) และเก็บข้อมูล 90 วัน + เอกสารภาษีของเรา 7 ปี เหตุผล: ยาวพอสำหรับรอบจ่ายของบัญชีบริษัทไทย (ปกติ 30 วัน) แต่ read-only ที่วัน 8 ทำให้ลูกค้าที่ยังใช้งานต้องจ่าย; ตรงกับ state ที่ payment-gateway §6.1 เสนอ (grace 7, suspended ถึง 60) และเพิ่ม read-only ตาม one-platform §2.5

**สิ่งที่ต้องทำถ้าเลือกตามคำแนะนำ:** (1) `Tenant.status` enum ตาม one-platform §2.3 + `PlatformSetting` สำหรับตัวเลขวัน (2) cron รายวันเปลี่ยนสถานะ + งาน export อัตโนมัติวันยกเลิก + งาน purge วัน 90 (มี dry-run และ log) (3) เขียนนโยบายนี้ลง Terms และหน้า "แพ็กเกจของฉัน" (4) ถามนักบัญชีเรื่องการเก็บเอกสาร VAT บน cloud (ท.ป.116/2545) ก่อนเปิดขาย (5) `PlatformInvoice` เก็บ PDF ที่ render ณ วันออก ใน storage แยกที่ไม่ถูก purge
