## 1. โปรเจกต์คืออะไร
- TMS (Transport Management System) ขายแบบ SaaS ให้บริษัทขนส่งทางบกในไทย ขนาด 10–200 คัน ที่มีทั้งรถบริษัทและรถร่วม
- Stack ฝั่งพัฒนา: NestJS / Prisma / PostgreSQL + Angular หรือ React (งานโค้ดทำใน Claude Code ไม่ได้อยู่ในขอบเขตของ Cowork)
- ทำเป็น **one platform**: ลูกค้าสมัครใช้งานเองได้, ทีมเราจัดการลูกค้าและผู้ใช้ผ่าน Platform Console, ฝั่งกลางกำหนดแพ็กเกจได้, และลูกค้าดูแพ็กเกจที่ตัวเองสมัครไว้ได้

## 2. ข้อตกลงที่ตัดสินแล้ว (ห้ามย้อนกลับ)
1. **ใช้งานแบบ standalone ได้ครบเป็นค่าเริ่มต้น** และเชื่อม ERP หรือโปรแกรมบัญชีได้หลายตัวแบบ optional (Express, PEAK, FlowAccount, KRS, SAP B1, API)
   - **KRS เป็นแค่ connector ตัวหนึ่ง** ห้ามใช้ KRS เป็นระบบอ้างอิงหลักในเอกสารหรือดีไซน์
2. ถ้าไม่มี ERP ตัว TMS ต้องทำเอกสารให้จบได้เอง ได้แก่ ใบวางบิล, ใบแจ้งหนี้/ใบกำกับภาษี, ใบเสร็จ, ใบลดหนี้/เพิ่มหนี้, รับชำระ, จ่ายรถร่วม และ 50 ทวิ แล้ว export ไฟล์ให้นักบัญชีได้
3. สถานะของเอกสารต้องแยกออกจากสถานะการซิงก์กับ ERP
4. ดีไซน์อ้างอิงแนว **Shipsy แบบใกล้เคียง ไม่ต้องเหมือนเป๊ะ**
   - ห้ามใช้โลโก้ ข้อความ หรือภาพของเขา
   - เป้าหมายคือให้ดูเป็นผลิตภัณฑ์จริง ไม่ดูเหมือน AI ทำ
5. brief ของดีไซน์ส่งเข้า Claude Design **ทีละรอบ** ตามลำดับใน `design-briefs.md` ห้ามส่งรวมรอบที่ 1 กับรอบอื่น
6. ห้ามผูกลูกค้าด้วยสัญญายาวพร้อมค่าปรับ และห้ามล็อกฟีเจอร์พื้นฐาน (ePOD, วางบิล) ไว้ที่แพ็กเกจสูง

## 5. งานที่มอบให้ Cowork
แต่ละงานต้องแยก **FACT (มีลิงก์ที่เปิดดูได้)** กับ **OPINION** ให้ชัด ห้ามเดาฟีเจอร์หรือราคาจากชื่อ เขียนภาษาไทย ศัพท์เทคนิคเป็นภาษาอังกฤษได้

### งาน A: Research ราคาตลาดไทย → `research/pricing-th.md`
- ราคาจริงของ TMS / GPS / ePOD ที่ขายในไทย: Logis Boy, NOSTRA Logistics, Treasure TMS, Hublink, EyeFleet, Cartrack, DTC, และเจ้าอื่นที่เจอ
  - ดูจากหน้าราคา, ใบเสนอราคาที่เผยแพร่, ข่าว, กระทู้, งานจัดซื้อภาครัฐ (e-GP)
- หน่วยคิดเงิน (ต่อคัน / ต่อ user / ต่อเที่ยว / เหมา), ค่าติดตั้ง, สัญญาขั้นต่ำ
- ผลลัพธ์: ตารางเปรียบเทียบ + ช่วงราคาที่แนะนำสำหรับแพ็กเกจ เริ่มต้น / มาตรฐาน / องค์กร (คิดต่อรถ active/เดือน)

### งาน B: ตรวจเลขนิติบุคคลตอนสมัคร → `research/company-verification-th.md`
- กรมพัฒนาธุรกิจการค้า (DBD) / data.go.th / กรมสรรพากร มี API หรือชุดข้อมูลให้ค้นด้วยเลขผู้เสียภาษี 13 หลักหรือไม่
- ได้ข้อมูลอะไรบ้าง (ชื่อ, ที่อยู่, สถานะ, สาขา), เงื่อนไขการใช้, อัตราจำกัดการเรียก, ค่าใช้จ่าย
- ทางเลือกถ้าไม่มี API: ผู้ให้บริการเอกชน หรือตรวจด้วยคนผ่านคิวอนุมัติ

### งาน C: เทียบ payment gateway ไทย → `research/payment-gateway-th.md`
- Omise (Opn), 2C2P, GB Prime Pay, KBank / SCB payment API, Stripe (ใช้ในไทยได้แค่ไหน)
- เทียบ: บัตร, PromptPay QR, การตัดเงินอัตโนมัติรายเดือน (recurring/subscription), ค่าธรรมเนียม, webhook, เอกสารสำหรับนักพัฒนา, การออกใบกำกับภาษีหรือ e-Tax Invoice
- ทางเลือกรับโอน + แนบสลิป และบริการตรวจสลิปอัตโนมัติ
- ผลลัพธ์: ตาราง + คำแนะนำ 1 ตัวเลือกหลักพร้อมเหตุผล

### งาน D: เอกสารให้ผู้บริหารตัดสินใจ → `research/decisions.md`
สรุปคำถามที่รอตัดสินใจ แต่ละข้อมีตัวเลือก ข้อดีข้อเสีย และคำแนะนำ (ใช้ผลจากงาน A–C):
1. หน่วยคิดเงิน: ต่อรถ active (แนะนำ) / ต่อเที่ยว / ต่อ user
2. สมัครแล้วใช้ได้ทันที หรือต้องรอทีมอนุมัติ
3. Payment gateway ที่ใช้ และจะรับโอน + แนบสลิปด้วยหรือไม่
4. ราคาและโควตาจริงของแต่ละแพ็กเกจ
5. ระยะ grace period เมื่อค้างชำระ และระยะเก็บข้อมูลหลังยกเลิก

### งาน E (เมื่อผู้ใช้ขอ): คุยกับเจ้าของ ERP / KRS
ร่างคำถามสำหรับผู้ให้บริการ ERP แต่ละราย:
- รับเอกสารแบบไหน
- มี API หรือต้อง import ไฟล์
- ใครเป็นผู้ออกเลขเอกสาร
- ถ้างวดบัญชีปิดแล้วจะจัดการอย่างไร
- วิธีดึงสถานะการรับชำระกลับมา

**ห้ามส่งอีเมลหรือข้อความแทนผู้ใช้โดยไม่ได้รับอนุญาต**
