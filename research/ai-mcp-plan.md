# แผนนำ AI และ MCP เข้ามาใช้ใน TMS

> เขียนเมื่อ 4 พ.ย. 2569 · ทั้งไฟล์เป็น OPINION (ข้อเสนอ) ยังไม่ได้วัดผลกับข้อมูลจริง
> เกี่ยวข้อง: `tms-product-learning.md`, `one-platform.md`, `design-briefs.md` (รอบ 11–14)

## 0. หลักที่ใช้ทุกฟีเจอร์
- **AI เสนอ แต่คนเป็นคนยืนยัน** งานที่กระทบเงิน เอกสารภาษี หรือการจ่ายงานรถ ต้องมีคนกดยืนยันเสมอ ผลลัพธ์ของ AI ถูกเก็บเป็น "ร่าง" ทุกครั้ง
- **งานคำนวณใช้เครื่องมือเฉพาะทาง** เช่น จัดเส้นทางและจัดรถใช้ solver (OR-Tools) ตรวจความผิดปกติของน้ำมันใช้สถิติ ส่วน AI ทำหน้าที่อธิบายผลและสรุปเป็นข้อความ
- **ข้อมูลแยกตามลูกค้า (tenant)** ทุกการเรียก AI ต้องบันทึก log และนับโควตาตามแพ็กเกจ
- **กัน prompt injection** ข้อความจากเอกสาร LINE หรืออีเมลที่ AI อ่านถือเป็นข้อมูลเท่านั้น AI ต้องไม่ทำตามคำสั่งที่อยู่ในข้อความเหล่านั้น
- **ปิด AI ได้รายลูกค้า** และปิดแยกรายฟีเจอร์ได้

## 2. MCP

### 2.1 TMS MCP Server (ตัวสำคัญ)
ให้ลูกค้าใช้ AI ที่ตัวเองมี (Claude, ChatGPT หรืออื่น ๆ) สั่งงาน TMS ได้

- ใช้ scope เดียวกับ Open API ยืนยันตัวตนด้วย OAuth หรือ API key แยกตาม tenant
- Tools แบบอ่านอย่างเดียว (ระยะ 2): ค้นหา SO/DO, ดูสถานะและตำแหน่งรถ, ขอ POD, ดูสถานะใบแจ้งหนี้และลูกหนี้, ดูสถานะรถและเอกสารใกล้หมด, ขอราคาจาก rate card, ดึงรายงาน
- Tools แบบเขียน (ระยะ 3): สร้าง SO ร่าง, เพิ่มหมายเหตุ, แจ้งเหตุ โดยทุก tool ต้องคืนผลเป็น "ร่างรอยืนยัน" ผู้ใช้ต้องยืนยันใน TMS ก่อนจึงจะมีผล
- รองรับ custom fields อัตโนมัติ
- มี rate limit และ audit log เหมือน Open API
- เปิดให้เฉพาะแพ็กเกจที่มี Open API

### 2.2 ผู้ช่วย AI ในระบบเรียก MCP ภายนอก (MCP client)
- ดึงใบสั่งงานจาก Google Drive หรืออีเมล
- เชื่อม LINE แผนที่ และระบบบัญชีหรือ ERP ที่มี MCP
- ใช้เป็นช่องทางเสริม ไม่ได้แทน connector เดิม

### 2.3 MCP ภายในสำหรับทีมเรา (ระยะ 3)
- ทีม support ถามสถานะลูกค้าจาก Platform Console และ log ได้
- อ่านอย่างเดียว และห้ามเข้าใช้งานแทนลูกค้า (impersonate) ผ่าน AI

## 3. โครงสร้างระบบ (NestJS / Prisma / PostgreSQL)
- **โมดูล `ai` กลาง:** เปลี่ยนผู้ให้บริการได้, บังคับผลลัพธ์เป็น JSON schema, ใช้ prompt caching, นับ token และค่าใช้จ่ายราย tenant, มีสวิตช์ปิดราย tenant และรายฟีเจอร์
- **เลือกรุ่นตามงาน** (ต้องวัดผลกับข้อมูลไทยก่อนตัดสินใจ):
  - Claude Haiku 5.5: คัดแยกและจัดหมวด
  - Claude Sonnet 5.5: ดึงข้อมูลจากเอกสารและรูป
  - Claude Opus 5.5: วิเคราะห์ซับซ้อนและผู้ช่วยวางแผน
- **ตาราง `AiSuggestion`:** tenantId, feature, entity, input ref, ค่าที่เสนอ (JSON), ความมั่นใจ, แหล่งที่มา (ข้อความหรือรูปตรงไหน), สถานะ (รอ/รับ/แก้แล้วรับ/ปฏิเสธ), ผู้ยืนยัน และเวลา ใช้วัดความแม่นต่อได้
- **ตาราง `AiUsage`:** นับ credit ต่อ tenant ต่อเดือน ผูกกับ `UsageRecord` ของแพ็กเกจ
- **MCP server เป็น service แยก:** เรียกผ่าน API layer เดียวกับ Open API ไม่ต่อฐานข้อมูลตรง
- **PDPA:**
  - แจ้งลูกค้าว่าข้อมูลส่งไปประมวลผลที่ไหน
  - ปิดบังข้อมูลส่วนบุคคลที่ไม่จำเป็น
  - ตั้งค่าไม่ให้ผู้ให้บริการ AI เก็บข้อมูล
  - มีตัวเลือกปิด AI สำหรับลูกค้าองค์กร
- **ชุดทดสอบภาษาไทย:** ใบสั่งงาน LINE, ใบเสร็จ และ POD จริง 200–500 ตัวอย่าง (ต้องได้รับอนุญาต) ใช้วัดความแม่นก่อนเปิดฟีเจอร์

## 4. แพ็กเกจ
- AI credit ต่อเดือน: เริ่มต้น 200 / มาตรฐาน 1,000 / องค์กร ตกลง และซื้อเพิ่มเป็น add-on ได้ (ตัวเลขเป็นตัวอย่าง)
- MCP server เปิดในแพ็กเกจมาตรฐานขึ้นไป (ตาม Open API)
- หน้าแพ็กเกจของลูกค้าแสดงแถบ "AI credit ที่ใช้"

## 5. ลำดับที่แนะนำ
| ระยะ | ทำอะไร | เหตุผล |
|---|---|---|
| 1 (พร้อม MVP) | ข้อ 1–5 | คุ้มที่สุดและเสี่ยงต่ำ เพราะ AI แค่ร่างให้คนยืนยัน |
| 2 | ข้อ 6, 7, 10 และ MCP server แบบอ่านอย่างเดียว | ต้องมีข้อมูลการใช้งานจริงก่อน |
| 3 | ข้อ 8, 9, 11, MCP แบบเขียน และ MCP ภายใน | ซับซ้อน ต้องมีระบบกันความผิดพลาดมากกว่า |

## 6. ต้องตัดสินใจ
1. เริ่มระยะ 1 พร้อม MVP เลย หรือรอให้ระบบหลักเสถียรก่อน
2. AI credit รวมในแพ็กเกจ หรือแยกขายเป็น add-on
3. ยอมให้ข้อมูลลูกค้าไปประมวลผลนอกประเทศได้หรือไม่ (ต้องเช็กเงื่อนไข PDPA กับลูกค้าองค์กร)
