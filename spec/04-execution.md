## 0. แนวคิดร่วมของโมดูล

### 0.1 สถานะ Trip / Stop ที่โมดูลนี้เปลี่ยน
enum เต็มอยู่ใน 10-data-model; 03 เป็นเจ้าของสถานะจนถึง `dispatched` ส่วน 04 เป็นเจ้าของการเปลี่ยนหลังจากนั้น

**Trip**

| จาก → ไป | เงื่อนไข | ใครทำ | ผลข้างเคียง |
|---|---|---|---|
| `dispatched` → `accepted` | คนขับกดรับ (M11) หรือ tenant ตั้ง "ไม่ต้องกดรับ" (auto) | คนขับ / ระบบ | event `trip.accepted` |
| `dispatched` → `rejected` | คนขับปฏิเสธพร้อมเหตุผล | คนขับ | กลับไปกระดานวางแผน (03) + ข้อยกเว้น `DRIVER_REJECTED` |
| `accepted` → `in_progress` | ตรวจรถก่อนออก (M7) ผ่านหรือผ่านแบบมีข้อบกพร่อง **และ** กด "ออกรถ" | คนขับ | `trip.started`, เริ่มเก็บตำแหน่ง, แจ้งลูกค้า "รถออก" เมื่อจุดรับแรกเสร็จ |
| `in_progress` → `completed` | ทุก stop อยู่ในสถานะสิ้นสุด (`completed/partial/failed/skipped`) | ระบบ | `trip.completed` |
| `completed` → `closed` | คนขับจบเที่ยว (M16) หรือ dispatcher ปิดแทน (เหตุผลบังคับ) | คนขับ / dispatcher | ล็อกเลขไมล์, ส่งยอดเงินทอนไป 05, หยุดเก็บตำแหน่ง |
| ใด ๆ (ก่อน `closed`) → `cancelled` | ยกเลิกจาก 03 | dispatcher | push ไปแอป M18 + ล้างงานในเครื่องเมื่อซิงก์ |

**Stop**

| สถานะ | ความหมาย | เข้าได้จาก |
|---|---|---|
| `pending` | ยังไม่ถึง | — |
| `en_route` | stop ถัดไปของรถที่กำลังวิ่ง | `pending` (อัตโนมัติเมื่อ stop ก่อนหน้าสิ้นสุด) |
| `arrived` | ถึงจุด (geofence หรือกดเอง) | `en_route`, `pending` |
| `working` | เริ่มขึ้น/ลงของ | `arrived` |
| `completed` | เสร็จพร้อม POD/หลักฐานครบตามที่ตั้ง | `arrived`, `working` |
| `partial` | ส่งบางส่วน | `arrived`, `working` |
| `failed` | ส่งไม่สำเร็จ ของยังอยู่บนรถ (E7) | `en_route`, `arrived`, `working` |
| `skipped` | dispatcher ข้ามจุด (เหตุผลบังคับ) | `pending`, `en_route` |

### 0.2 เวลาสองชุดในทุก event [DECISION]
- `occurredAt` = เวลาที่เกิดจริงบนเครื่อง/อุปกรณ์ (ใช้แสดงผล คิดค่ารอ OTIF)
- `receivedAt` = เวลาที่ server ได้รับ (ใช้ audit และวัด lag)
- รายงานทุกตัวใช้ `occurredAt`; ถ้าถูกแก้ด้วยมือ เก็บค่าเดิม + ผู้แก้ + เหตุผล

### 0.3 แหล่งตำแหน่งรถ
| แหล่ง | ใช้กับ | ความถี่ | หมายเหตุ |
|---|---|---|---|
| GPS provider connector (กล่อง GPS ที่ติดตามมาตรฐานกรมการขนส่งทางบก) | รถบริษัท/รถร่วมที่ผูก connector | ตามผู้ให้บริการ (pull ทุก 60 วิ หรือ push) | ยี่ห้อ/ API แต่ละค่ายยังไม่ยืนยัน → [OPEN] EXE-Q2 |
| แอปคนขับ (มือถือ) | ทุกคนขับที่มีแอป (สำคัญกับรถร่วมที่ไม่มี connector — E5) | adaptive (DRV-062) | เก็บเฉพาะช่วง "ปฏิบัติงาน" (DRV-091) |
| หน้ารถร่วม (เว็บ) | รถร่วมไม่ลงแอป | เฉพาะตอนกดปุ่มสถานะ | ไม่ใช่ tracking ต่อเนื่อง |

## 1. EXE-A หน้าติดตามรถ (Live tracking)

**1. จุดประสงค์** — ให้ dispatcher เห็นรถทุกคันที่มีเที่ยววันนี้บนแผนที่ พร้อม ETA และสัญญาณผิดปกติ (ล่าช้า/ออกนอกเส้นทาง/จอดนาน/สัญญาณขาด) ในจอเดียว

**2. ผู้ใช้/สิทธิ์**

|---|---|---|---|
| dispatcher, manager, admin | ✓ | ✓ | ✓ |
| accounting, fleet, viewer | ✓ | — | fleet ✓ |

**3. หน้าจอ** (ปฏิบัติการ → ติดตามรถ)
- แถบตัวกรองบน: ความเป็นเจ้าของ (ทั้งหมด / รถบริษัท / รถร่วม), สถานะ (วิ่งอยู่ / จอด / ล่าช้า / ออกนอกเส้นทาง / จอดนาน / สัญญาณขาด / ยังไม่ออก), ลูกค้า, ประเภทรถ, สาขา, ค้นหา (ทะเบียน, เลขเที่ยว, เลข DO, คนขับ)
- ซ้าย: รายการรถ (กว้าง 360px) แถวละ 3 บรรทัด — ทะเบียน + ประเภท + ป้ายรถร่วม / คนขับ · stop ถัดไป / ETA + ป้ายสถานะ + "อัปเดต X นาทีที่แล้ว"
- กลาง: แผนที่ หมุดรถหมุนตาม heading, สีตามสถานะ, cluster เมื่อซูมออก; เส้นทางแผนของเที่ยวที่เลือก (เส้นประ) + เส้นทางจริง (เส้นทึบ)
- ขวา: drawer เที่ยวรถ (มาตรฐาน 600px) แท็บ สรุป / จุดรับส่ง (timeline: แผน vs จริง, ETA ต่อจุด, เวลารอ) / ข้อยกเว้น / กิจกรรม; ปุ่ม "โทรหาคนขับ", "ส่งข้อความ" (→ M18), "ดูเส้นทางย้อนหลัง"
- KPI บรรทัดเดียวเหนือรายการ: วิ่งอยู่ · ล่าช้า · ข้อยกเว้นเปิด · สัญญาณขาด (คลิกกรอง)
- Empty state: "วันนี้ยังไม่มีเที่ยวที่ออกวิ่ง" + ลิงก์ไปกระดานวางแผน

**5. กฎธุรกิจ**
- **EXE-001** แผนที่ต้องใช้ tile/geocoding/routing provider ที่ **อนุญาตใช้เชิงพาณิชย์** และมีสัญญา/โควตาชัดเจน; ห้ามใช้ tile สาธารณะของ OSM (tile.openstreetmap.org/.de) ใน production — ต้นแบบรอบ 7 ใช้ tile.openstreetmap.de ชั่วคราวเท่านั้น ตัวเลือก (MapTiler, Mapbox, Google Maps Platform, Longdo Map, self-host OSM) → [OPEN] EXE-Q1
- **EXE-002** แหล่งตำแหน่งมีลำดับ: GPS provider (ถ้าอายุ ≤ 5 นาที) > แอปคนขับ > หน้ารถร่วม; ตำแหน่งที่แสดงคือจุดล่าสุดตามลำดับนี้ และแสดงแหล่งในทูลทิป
- **EXE-003** ETA ต่อ stop = เวลาวิ่งจาก routing API (ตำแหน่งปัจจุบัน → stop ถัดไป → …) + เวลาให้บริการต่อจุด (ค่าเริ่มต้นจากสถานที่ 02 หรือ 30 นาที); ถ้า routing ไม่ตอบ ใช้ระยะเส้นตรง × 1.3 ÷ 50 กม./ชม. และติดป้าย "ETA โดยประมาณ" [PROPOSED]
- **EXE-004** คำนวณ ETA ใหม่เมื่อ (ก) ได้ตำแหน่งใหม่ที่ห่างจากครั้งก่อน ≥ 1 กม. หรือ (ข) ผ่านไป 5 นาที (เฉพาะรถ `moving`) หรือ (ค) stop เปลี่ยนสถานะ — จำกัดการเรียก routing ≤ 1 ครั้ง/2 นาที/เที่ยว
- **EXE-005** **ล่าช้า**: `etaAt` ของ stop > ปลายช่วงเวลานัด + ค่าเผื่อ (ค่าเริ่มต้น 15 นาที ตั้งต่อลูกค้าได้) → ติดธง `late` + สร้างข้อยกเว้น `LATE_ETA` (EXE-020)
- **EXE-006** **ออกนอกเส้นทาง**: ระยะจากเส้นทางแผน > 2 กม. ต่อเนื่อง ≥ 10 นาที (ตั้งค่าได้) และ accuracy ≤ 200 m → ธง `off_route`; เที่ยวที่ไม่มีเส้นทางแผน (ไม่มี routing) ไม่ตรวจข้อนี้
- **EXE-007** **จอดนาน**: ความเร็ว < 5 กม./ชม. ต่อเนื่อง ≥ 30 นาที (ตั้งค่าได้) **นอก** geofence ของ stop และนอก "จุดพักที่อนุญาต" (สถานที่ประเภทจุดพัก/ปั๊ม ใน 02) → ธง `long_stop`
- **EXE-008** **สัญญาณขาด**: เที่ยว `in_progress` ไม่มีตำแหน่งใหม่ ≥ 30 นาที → `no_signal` (ไม่สร้างข้อยกเว้นจนครบ 60 นาที เพราะแอปอาจออฟไลน์ตามปกติ)
- **EXE-009** ธงหายเองเมื่อเงื่อนไขหายและข้อยกเว้นที่ผูกไว้ปิดอัตโนมัติด้วยเหตุผล `auto_cleared` (ดู EXE-024)
- **EXE-010** รถร่วมเห็นใน "รถร่วม" เมื่อ vehicle.ownership = `SUBCONTRACT`; ถ้ารถร่วมไม่มีแหล่งตำแหน่ง แสดงในรายการด้วยสถานะ "ไม่มีตำแหน่ง" และใช้เวลาที่กดสถานะจากหน้ารถร่วมแทน
- **EXE-011** ตำแหน่งดิบเก็บ 90 วัน แล้วเหลือเฉพาะสรุป (ระยะทางรายเที่ยว/รายวัน) [PROPOSED ตาม thai-tax-docs-research §5.4 OPINION]; ตั้งต่อ tenant ได้ 30–365 วัน
- **EXE-012** หน้า tracking อัปเดตแบบ push (WebSocket/SSE) ทุกครั้งที่มีตำแหน่งใหม่ ไม่เกิน 1 ครั้ง/10 วินาที/รถ ต่อผู้ชม

**6. สถานะ** — `trackingState` คำนวณ ไม่มี transition ที่ผู้ใช้สั่ง
| จาก → ไป | เงื่อนไข |
|---|---|
| `not_started` → `moving` | trip `in_progress` และ speed ≥ 5 |
| `moving` ↔ `stopped` | speed < 5 ≥ 3 นาที / speed ≥ 5 |
| ใด ๆ → `no_signal` | ไม่มีตำแหน่ง ≥ 30 นาที |
| `no_signal` → `moving/stopped` | ได้ตำแหน่งใหม่ |

**7. Event** — `tracking.position_received` (ภายใน ไม่ส่ง webhook รายจุด), `tracking.eta_changed` (เปลี่ยน ≥ 10 นาที; webhook `shipment.eta_updated`), `tracking.flag_raised`, `tracking.flag_cleared`

**8. กรณีผิดปกติ**
| กรณี | การจัดการ |
|---|---|
| GPS provider ส่งตำแหน่งย้อนเวลา | เก็บ แต่ไม่ใช้แทนตำแหน่งล่าสุดถ้า occurredAt เก่ากว่า |
| สองแหล่งขัดกัน > 5 กม. ในเวลาเดียวกัน | ใช้ GPS provider + บันทึก `source_conflict` ให้ fleet ตรวจ (มือถืออาจไม่ได้อยู่บนรถ) |

### 1.1 EXE-A2 โหมดแสดงผล 3 มิติ [PROPOSED · P2 — เฟสเดียวกับ GPS/แอปคนขับ, `plan/05` D-51] (เพิ่ม 10 พ.ย. 2569 จากต้นแบบรอบ 19)

**1. จุดประสงค์** — มุมมองทางเลือกของหน้า EXE-A สำหรับห้องควบคุม/จอใหญ่/เดโมขาย: แผนที่มุมเอียงพร้อมรถบรรทุก 3 มิติที่วิ่งตามถนนจริง ใช้ข้อมูลชุดเดียวกับ 2 มิติทุกประการ ไม่มีฟังก์ชันที่ทำได้เฉพาะใน 3 มิติ (ยกเว้น "ติดตามคันนี้" แบบกล้องตาม)

**2. หลัก**
- **EXE-013** 3 มิติเป็น *view mode* ของหน้าเดียวกัน: ตัวกรอง, รายการ, drawer, KPI, สิทธิ์ `tracking.*`, ธง `late|off_route|long_stop|no_signal` และ event เหมือน EXE-A; สลับได้ด้วยปุ่ม 2D/3D และจำค่าต่อผู้ใช้; ค่าเริ่มต้น 2 มิติบนมือถือ, บนเครื่องไม่มี WebGL2, และเมื่อ `prefers-reduced-motion`
- **EXE-014** เส้นทางแผนต้องเป็น geometry ตามถนนจาก routing provider ที่เก็บบนเที่ยว (`trip.planned_route`, คำนวณตอน dispatch และเมื่อ stop เปลี่ยน); เที่ยวที่ไม่มี geometry แสดงเส้นประตรงพร้อมป้าย "ไม่มีเส้นทางแผน" และไม่ให้รถ "วิ่ง" ตามเส้นนั้น (ห้ามจำลองการวิ่งที่ไม่มีข้อมูล)

**5. กฎธุรกิจ**
- **EXE-020** ระบบสร้างข้อยกเว้นจาก rule engine ตามตาราง 2.1; ถ้ามี `dedupKey` ที่ยังเปิดอยู่ ให้เพิ่ม `occurrences` + บันทึกกิจกรรม แทนการสร้างใหม่
- **EXE-021** "รับเรื่อง" = ตั้ง owner เป็นตัวเอง + สถานะ `in_progress`; "มอบหมาย" ต้องมีสิทธิ์ `exception.assign` และผู้รับต้องมีสิทธิ์ประเภทนั้น
- **EXE-022** SLA นับจาก `createdAt` เป็นนาทีปฏิทิน (ยกเว้นประเภทที่ระบุ "วันทำการ" ใช้ปฏิทินวันทำการของ tenant); เกิน SLA → แจ้งเจ้าของ + manager (in-app + LINE ถ้าเปิด) ครั้งเดียว และติด `slaBreachedAt`
- **EXE-023** ปิดเรื่องด้วยคนต้องเลือก `resolutionCode` + note ≥ 10 ตัวอักษร; ประเภท `PRETRIP_FAILED`, `OVERWEIGHT`, `ACCIDENT` ปิดได้เฉพาะ manager
- **EXE-024** ปิดอัตโนมัติเมื่อเงื่อนไขหาย (คอลัมน์ "ปิดอัตโนมัติเมื่อ") ด้วย code `auto_cleared` — ถ้ามีคนรับเรื่องแล้ว (`in_progress`) ไม่ปิดเอง แต่แจ้งเจ้าของว่า "เหตุหายแล้ว"
- **EXE-025** resolutionCode ต่อประเภท (ค่าเริ่มต้น): ล่าช้า → `customer_informed | rescheduled | traffic | no_action`; ส่งไม่สำเร็จ → `redeliver | return_to_origin | cancel_do`; POD → `pod_received | waived_by_manager | billing_hold`; ตรวจรถ → `vehicle_swapped | repaired | override_by_manager` ฯลฯ — tenant เพิ่มได้ (reason master 02)
- **EXE-026** เปิดใหม่ (reopen) ได้ภายใน 7 วันหลังปิด (เหตุผลบังคับ) สถานะกลับเป็น `in_progress` และ SLA เริ่มนับใหม่
- **EXE-027** ข้อยกเว้น `POD_INCOMPLETE`/`POD_MISMATCH` ที่ยังเปิด → DO ติดธง "ห้ามวางบิล" (05) จนกว่าจะปิดด้วย code ที่ไม่ใช่ `billing_hold`

**8. กรณีผิดปกติ** — rule engine ยิงซ้ำถี่ (ETA แกว่ง) → hysteresis: ต้องผ่านเกณฑ์ 2 รอบติดกันก่อนสร้าง และปิดอัตโนมัติหลังหายต่อเนื่อง 10 นาที · ผู้รับผิดชอบถูกปิดบัญชี → เรื่องกลับเป็น "ยังไม่มีเจ้าของ" + แจ้ง manager · สองคนกดรับพร้อมกัน → optimistic lock (`version`) คนที่สองได้ข้อความ "มีผู้รับเรื่องแล้ว"

**9. เกณฑ์ตรวจรับ**

- Given SLA 15 นาทีครบ When ยังไม่มีใครรับ Then แจ้ง manager 1 ครั้งและแถวเป็นสีแดง "เกิน"
- Given POD_MISMATCH เปิด When บัญชีเลือก DO นั้นในวางบิล Then ระบบแจ้งว่าติดข้อยกเว้นและไม่ให้เลือก

**5. กฎธุรกิจ**
- **EXE-040** trigger: `departed` = stop รับแรกของ DO เป็น `completed` และรถเคลื่อนออกจาก geofence; `eta_30` = ETA ถึง stop ส่งของ DO ≤ `etaLeadMinutes` (ส่งครั้งเดียวต่อ stop แม้ ETA แกว่ง); `delivered` = stop ส่ง `completed`/`partial` และ POD ถึง server ครบ (ถ้ารูปยังไม่ขึ้น รอสูงสุด 2 ชม. แล้วส่งโดยไม่มี POD)
- **EXE-041** ส่งเฉพาะเมื่อมีการ opt-in ที่ระดับลูกค้าหรือบริษัท และผู้รับมีข้อมูลช่องทางนั้น
- **EXE-042** ช่องทาง LINE ส่งผ่าน LINE Official Account ของ tenant (Messaging API) — ผู้รับต้องเป็นเพื่อนกับ OA และผูก userId (ผ่านลิงก์ผูกบัญชีในหน้าติดตาม); ไม่ผูก → fallback SMS ถ้าเปิดไว้; กลไกผูก/ค่าใช้จ่าย LINE → [OPEN] EXE-Q3
- **EXE-043** SMS/LINE นับโควตาตามแพ็กเกจ (`UsageRecord metric=sms|line_msg`); เกินโควตาและไม่มี add-on → `skipped_quota` + แจ้ง admin 1 ครั้ง/วัน; อีเมลไม่นับโควตา [PROPOSED]
- **EXE-044** ทุกข้อความแนบ `trackingUrl` (EXE-D); ข้อความไม่มีราคา ชื่อเต็ม/เบอร์คนขับ หรือทะเบียนเต็ม (ใช้ `plateMasked` เช่น "71-04xx กทม.")
- **EXE-045** SMS มีลิงก์/คำสั่งยกเลิกรับข้อความ; ผู้รับที่ยกเลิก → `skipped_optout` ทุก event ของ tenant นั้น (เก็บเป็น opt-out list ต่อเบอร์) — ฐาน PDPA ของการส่ง (ประโยชน์โดยชอบด้วยกฎหมาย/สัญญา) ต้องให้ที่ปรึกษายืนยัน [OPEN] EXE-Q4
- **EXE-046** การส่งเป็น async job, retry 3 ครั้ง (1, 5, 15 นาที); `eta_30` ที่ส่งไม่ทันก่อน stop `arrived` → ยกเลิก (ไม่ส่งข้อความหลังถึงแล้ว)

**6. สถานะ** — `queued → sent → delivered` (เมื่อ provider ตอบ DLR) · `queued/sent → failed` (หลัง retry ครบ) · `queued → skipped_*`

**7. Event** — `notification.customer_sent`, `notification.customer_failed` (audit); webhook ฝั่ง shipment ใช้ event เดิม (`shipment.picked_up`, `shipment.eta_updated`, `shipment.delivered`)

**9. เกณฑ์ตรวจรับ**
- Given ลูกค้า A เปิด SMS เฉพาะ `delivered` When ส่งสำเร็จ Then ผู้รับได้ SMS 1 ข้อความมีลิงก์ติดตาม และไม่มี SMS `departed`
- Given ETA แกว่ง 31 → 29 → 32 → 28 นาที Then ส่ง `eta_30` ครั้งเดียว
- Given โควตา SMS เดือนนี้หมด Then ข้อความเป็น `skipped_quota` และ admin เห็นแจ้งเตือน

**10. เฟส** — P0 อีเมล + SMS · P1 LINE OA

## 4. EXE-D หน้าติดตามสำหรับผู้รับ (สาธารณะ)

**1. จุดประสงค์** — หน้าเว็บมือถือที่ผู้ส่ง/ผู้รับเปิดจากลิงก์โดยไม่ login เพื่อดูสถานะ ETA และ POD ของ DO ตัวเอง (E9)

**2. ผู้ใช้/สิทธิ์** — ใครก็ได้ที่ถือลิงก์ token; ค้นด้วยเลข DO ต้องยืนยันตัว (EXE-062) · ภายใน: dispatcher สร้างใหม่/เพิกถอนลิงก์ (`do.edit`)

**3. หน้าจอ** (`/t/{token}`, 390px ก่อน)
- หัว: โลโก้ + ชื่อบริษัทขนส่ง (branding tenant), เลข DO, ชื่อผู้ส่ง (ชื่อลูกค้า)
- stepper: รับงานแล้ว → รถออกแล้ว → ใกล้ถึง → ส่งแล้ว (หรือ "ส่งไม่สำเร็จ — บริษัทจะติดต่อกลับ")
- ETA เป็นช่วงเวลา ("ประมาณ 10:30–11:00") + เวลาอัปเดตล่าสุด
- แผนที่ตำแหน่งรถ **เฉพาะเมื่อ stop นี้เป็น stop ถัดไป** (P1) แสดงตำแหน่งปัดเศษ 3 ตำแหน่ง
- สินค้า: รายการ + จำนวน (ไม่มีราคา)
- POD (เมื่อส่งแล้ว): รูป (thumbnail กดขยาย), ลายเซ็น, ชื่อผู้รับ, เวลาส่ง, จำนวนที่ส่งจริง
- ฟิลด์เพิ่มเติมที่ตั้ง "แสดงในหน้าติดตาม" (02 custom fields)
- ปุ่ม "โทรหาบริษัทขนส่ง" (เบอร์บริษัท ไม่ใช่เบอร์คนขับ), สลับภาษา TH/EN/中文
- state: ลิงก์หมดอายุ / ถูกเพิกถอน / ไม่พบ → หน้าเดียวกัน "ลิงก์นี้ใช้ไม่ได้ กรุณาติดต่อ {companyPhone}"

## 6. DRV-A แอปคนขับ: หลักร่วม

## 7. DRV-SYNC กติกาออฟไลน์และการซิงก์ (E1)

**1. จุดประสงค์** — ให้คนขับทำงานต่อได้ในที่ไม่มีสัญญาณ โดยข้อมูลไม่หาย ไม่ซ้ำ และลำดับเวลาถูกต้อง

**2. ผู้ใช้** — แอปคนขับ, server API `/driver/v1/sync`

**3. หน้าจอ** — M17 (ข้อ 19) + ไอคอน sync

**4. ฟิลด์ — `DriverEvent` (outbox item)**
| ชื่อ | ชนิด | บังคับ | กฎตรวจ | หมายเหตุ |
|---|---|---|---|---|
| clientEventId | uuid v4 (สร้างบนเครื่อง) | ✓ | unique ต่อ tenant | idempotency key |
| type | enum (ตารางล่าง) | ✓ | | |
| tripId / stopId / doId | uuid | ตาม type | | |
| occurredAt | timestamptz (เวลาเครื่อง) | ✓ | | |
| deviceClockOffsetMs | int | ✓ | | ค่าต่างเวลาเครื่อง−server จากการซิงก์ครั้งล่าสุด |
| location | {lat,lng,accuracyM} | — | | ทุก event ที่มีสิทธิ์ตำแหน่ง |
| payload | jsonb | ✓ | ตาม schema ของ type + version | |
| fileRefs | clientFileId[] | — | | รูป/ลายเซ็นที่ผูก |
| baseVersion | int | — | | version ของ stop/trip ที่เครื่องเห็นตอนบันทึก |
| appVersion, deviceId | string | ✓ | | |
| receivedAt | timestamptz | server | | |

**ประเภท event:** `trip.accept`, `trip.reject`, `pretrip.submit`, `trip.start`, `stop.arrive`, `stop.work_start`, `stop.work_finish`, `stop.depart`, `pickup.submit`, `pod.submit`, `stop.fail`, `issue.report`, `expense.submit`, `trip.end`, `message.read`, `message.reply`, `location.batch`, `customfield.update`

**5. กฎธุรกิจ**
- **DRV-060** ทุกการกระทำของคนขับบันทึกลง outbox ในเครื่องก่อน (SQLite เข้ารหัส) แล้ว UI แสดงผลทันที (optimistic) — ไม่มีการกระทำใดที่ต้องรอเน็ตยกเว้น M1 login ครั้งแรก
- **DRV-061** server รับ event แบบ idempotent: `clientEventId` ซ้ำ → ตอบ 200 พร้อมผลเดิม ไม่ประมวลผลซ้ำ (ห้ามทำแบบ X12 LogisticsX)
- **DRV-062** ตำแหน่ง adaptive (X8): วิ่ง 60 วิ, ห่าง stop ถัดไป < 2 กม. ทุก 15 วิ, จอด ≥ 3 นาที ทุก 5 นาที; ส่งเป็น batch ทุก 2 นาทีหรือเมื่อครบ 50 จุด
- **DRV-063** ส่ง outbox ตามลำดับ `occurredAt` ทีละ batch (≤ 50 event); event ที่อ้าง `fileRefs` ส่งได้ก่อนรูปขึ้นเสร็จ — server เก็บสถานะ "รอไฟล์" และ POD ถือว่า "ครบ" เมื่อไฟล์ครบ
- **DRV-064** รูป: บีบอัดบนเครื่องด้านยาว ≤ 1600px JPEG คุณภาพ ~0.7 (เป้า ≤ 500 KB), เก็บ EXIF เวลา+พิกัด, อัปโหลดแบบ resumable ด้วย `clientFileId` (idempotent), ใช้ Wi-Fi/มือถือได้ทั้งคู่; ลายเซ็นเก็บเป็น PNG/SVG
- **DRV-065** retry: backoff 5 วิ → 30 วิ → 2 นาที → 5 นาที (สูงสุด) ไม่จำกัดครั้งจนกว่า server ตอบ 4xx ที่ไม่ใช่ 408/429; 4xx ถาวร → item สถานะ "ส่งไม่สำเร็จ" ใน M17 พร้อมข้อความเหตุผล
- **DRV-066** เวลา: ใช้ `occurredAt` จากเครื่อง; ถ้า |deviceClockOffsetMs| > 5 นาที server แก้เป็น `occurredAt − offset` และติดธง `clock_adjusted`; ถ้าไม่เคยซิงก์เวลาเลย ใช้เวลาจาก GPS fix ถ้ามี
- **DRV-067** server ตรวจลำดับตรรกะ (เช่น `pod.submit` ก่อน `stop.arrive`) — ถ้าขาด event ก่อนหน้า ให้สร้าง event อนุมาน (`inferred=true`, เวลาเดียวกับ event ที่มาถึง) แทนการปฏิเสธ
- **DRV-068** การดาวน์โหลดลงเครื่อง: เที่ยววันนี้ + พรุ่งนี้ (สถานะ ≥ dispatched), สถานที่/geofence, POD profile ของลูกค้าในเที่ยว, checklist ตรวจรถของประเภทรถ, reason master, expense types, custom field schema, i18n — ซิงก์ทุกครั้งที่มีเน็ต + push trigger เมื่อ dispatcher เปลี่ยนงาน
- **DRV-069** ข้อมูลในเครื่องเข้ารหัส (SQLCipher/Keystore/Keychain); ลบเที่ยวที่ `closed` และซิงก์ครบแล้วออกจากเครื่องหลัง 7 วัน

**กติกาเมื่อขัดกัน (conflict)**
| กรณี | กติกา |
|---|---|
| **DRV-070** dispatcher แก้ข้อมูลงาน (เวลา/ที่อยู่/ลำดับ stop) ขณะคนขับออฟไลน์ | server ชนะสำหรับข้อมูลแผน; เมื่อซิงก์ แอปแสดง M18 "งานถูกแก้ไข" + highlight ส่วนที่เปลี่ยน |
| **DRV-071** คนขับบันทึกผลหน้างาน (arrive/POD/fail) | ข้อมูลจริงหน้างานชนะเสมอ ไม่ถูกเขียนทับด้วยแผน |
| **DRV-072** stop/DO ถูกยกเลิกหรือย้ายไปเที่ยวอื่นก่อนที่ event ของคนขับมาถึง | รับ event เก็บเป็นประวัติ (ไม่ทิ้งหลักฐาน) แต่ไม่เปลี่ยนสถานะ DO; สร้าง `OFFLINE_CONFLICT` ให้ dispatcher ตัดสิน |
| **DRV-073** event เดียวกันจาก 2 เครื่อง (คนขับร่วม E8) สำหรับ stop เดียว | `occurredAt` ก่อนชนะสำหรับ arrive; POD รับทั้งคู่ถ้าต่าง `clientEventId` แล้ว POD ที่สองติดธงซ้ำให้ตรวจ |
| **DRV-074** ออฟไลน์เกิน `offlineMaxHours` | แอปยังบันทึกต่อได้ แต่แสดงแบนเนอร์ "ไม่ได้ส่งข้อมูลมา X ชม. — กรุณาหาสัญญาณ"; server สร้าง `NO_SIGNAL` อยู่แล้ว |
| **DRV-075** stop ถูกปิดแทนโดย dispatcher (บันทึกแทน) แล้ว event คนขับมาถึงทีหลัง | เก็บทั้งสองชุด ใช้ข้อมูลคนขับเป็นหลักฐาน POD และเวลาของคนขับถ้ามีพิกัดใน geofence; สร้าง `OFFLINE_CONFLICT` ถ้าจำนวนส่งต่างกัน |

**6. สถานะ outbox item** — `pending → sending → synced` · `sending → pending` (เน็ตหลุด) · `sending → failed` (4xx ถาวร) · `failed → pending` (กดลองใหม่) · ไฟล์: `queued → uploading → uploaded`

**7. Event** — server ส่ง event ธุรกิจตาม type (เช่น `shipment.arrived`, `pod.uploaded`) ด้วย `occurredAt` จากเครื่อง; เพิ่ม `driver.sync_completed` (ภายใน)

**8. กรณีผิดปกติ** — เครื่องเต็ม (< 200 MB) → เตือนและหยุดถ่ายรูปความละเอียดสูง (ลด 1024px) · ติดตั้งแอปใหม่ทั้งที่มีคิวค้าง → คิวหาย: ป้องกันด้วยการบล็อก logout (DRV-140) และแจ้งในหน้าติดตั้ง · schema version ไม่ตรง → server รับ payload version เก่า ≥ 2 รุ่นย้อนหลัง; เก่ากว่านั้นบังคับอัปเดตแอปแต่ยังส่งคิวเก่าได้

**9. เกณฑ์ตรวจรับ**
- Given โหมดเครื่องบิน When คนขับ ถึงจุด → ถ่ายรูป 3 รูป → เซ็น → ส่ง POD Then จอ M5 แสดงสำเร็จ และ M17 มี 1 event + 3 ไฟล์ + 1 ลายเซ็น รอส่ง
- Given ส่ง event เดิมซ้ำ 3 ครั้ง (`clientEventId` เดียว) Then DB มีผลครั้งเดียว
- Given นาฬิกาเครื่องเร็ว 20 นาที When ซิงก์ Then `occurredAt` ถูกปรับและมีธง `clock_adjusted`
- Given DO ถูกยกเลิกระหว่างที่คนขับออฟไลน์และส่ง POD ไปแล้ว Then POD ถูกเก็บ, DO ยังเป็นยกเลิก, มี `OFFLINE_CONFLICT`

**10. เฟส** — P0 (ทั้งหมด)

## 11. DRV-M7 ตรวจรถก่อนออก (Pre-trip inspection)

**1. จุดประสงค์** — คนขับตรวจสภาพรถ/หางตาม checklist ก่อนออกเที่ยวแรกของวัน ข้อวิกฤตผิดปกติแล้วห้ามออกรถ (ผลไปหน้า "ผลตรวจรถก่อนออก" ใน 06 FLT-F)

**2. ผู้ใช้** — driver; fleet บันทึกแทนได้ในเว็บ (06)

**3. หน้าจอ** — หัว: ทะเบียน (+ หาง) + เลขไมล์ล่าสุดในระบบ; ช่อง "เลขไมล์เริ่มต้น" (ตัวเลข, คีย์บอร์ดตัวเลข); ปุ่ม "ปกติทั้งหมด"; รายการตรวจแบ่งหมวด (ภายนอก/ยาง/ไฟ/ของเหลว/ห้องโดยสาร/อุปกรณ์ความปลอดภัย/หาง) แต่ละข้อ segmented control 2 ค่า **ปกติ | ผิดปกติ** ข้อวิกฤตมีไอคอนเตือน; เลือก "ผิดปกติ" → แถวขยาย: ถ่ายรูป (≥ 1, บังคับ) + หมายเหตุ (บังคับ); สรุปท้ายจอ "ผิดปกติ N ข้อ (วิกฤต M)"; ปุ่มหลัก "ส่งผลตรวจ"

**4. ฟิลด์ — `PreTripInspection` / `PreTripItemResult`**

**5. กฎธุรกิจ**
- **DRV-130** "ปกติทั้งหมด" ตั้งทุกข้อที่ยังไม่ได้เลือกเป็น `normal` (ไม่ทับข้อที่เลือก `abnormal` แล้ว)
- **DRV-131** ผล: มีข้อวิกฤต `abnormal` ≥ 1 → `fail`; มีแต่ข้อไม่วิกฤต → `pass_with_defects`; ไม่มี → `pass`
- **DRV-132** `fail` → ปุ่ม "ออกรถ" ล็อก, จอแสดง "ห้ามออกรถ — แจ้งฝ่ายจัดรถแล้ว", สร้าง `PRETRIP_FAILED` + defect ใน 06 + รถติดกฎห้ามจ่ายงาน `PRETRIP_CRITICAL_FAIL` (03) จนกว่าจะซ่อม/ตรวจซ้ำผ่าน หรือ manager override (เหตุผลบังคับ, audit)
- **DRV-133** ต้องตรวจ 1 ครั้งต่อรถต่อวัน (ตามเวลาท้องถิ่น) ก่อนเที่ยวแรก; เที่ยวถัดไปในวันเดียวกันไม่ต้องตรวจซ้ำ เว้นแต่เปลี่ยนคนขับหรือเปลี่ยนหาง (ตรวจเฉพาะหมวดหาง)
- **DRV-134** ออฟไลน์: ผล `fail` ล็อกปุ่มออกรถในเครื่องทันที; การ override จาก manager ต้องรอซิงก์ (หรือให้ dispatcher เปลี่ยนรถ)
- **DRV-135** ใช้ `startOdometerKm` เป็นเลขไมล์ต้นเที่ยว (ส่ง 06 FLT-O)

**6. สถานะ** — inspection: `draft (ในเครื่อง) → submitted`; ผลกระทบ trip ดู §0.1

**7. Event** — `vehicle.pretrip_submitted` (payload result, defects), `vehicle.pretrip_failed`

**8. กรณีผิดปกติ** — template ของประเภทรถยังไม่ตั้ง → ใช้ template มาตรฐานของระบบ · กล้องถูกปฏิเสธ → state "ไม่ให้สิทธิ์กล้อง" (ข้อ 23) และส่งผลข้อ abnormal ไม่ได้ · เลขไมล์ต่ำกว่าล่าสุด → ไม่ให้ส่ง ข้อความ "เลขไมล์ต่ำกว่าครั้งล่าสุด (123,450) — ตรวจอีกครั้ง หรือแจ้งฝ่ายรถ" + ลิงก์ "เรือนไมล์ถูกเปลี่ยน" (บันทึกเหตุผล → ส่งให้ fleet ยืนยัน)

**9. เกณฑ์ตรวจรับ**
- Given 20 ข้อ When กด "ปกติทั้งหมด" แล้วเปลี่ยน "เบรก" (วิกฤต) เป็นผิดปกติโดยไม่แนบรูป Then ปุ่มส่งเทา "ต้องถ่ายรูปข้อที่ผิดปกติ"
- Given ส่งผล fail Then ปุ่ม "ออกรถ" ล็อก, เว็บมีข้อยกเว้น critical, กระดานวางแผนแสดงรถคันนี้ติดกฎ
- Given ตรวจผ่านเช้านี้ When เที่ยวที่ 2 บ่าย Then ไม่ต้องตรวจซ้ำ

**10. เฟส** — P0

- **DRV-160** ขั้นบังคับคำนวณจาก PodProfile ของลูกค้าของ DO; หลาย DO ที่ stop เดียวกัน (ต่างลูกค้า) → ทำ POD แยกต่อ DO แต่ลายเซ็น/รูปใบส่งของใช้ร่วมได้เมื่อผู้รับคนเดียวกัน (ปุ่ม "ใช้กับ DO อื่นในจุดนี้")
- **DRV-161** deliveredQty < loadedQty และ > 0 → stop `partial` + ส่วนต่างเข้ากระบวนการ M13 (ของคืน/ส่งใหม่); deliveredQty = 0 ต้องใช้ M13
- **DRV-162** COD: codCollected ≠ codExpected → เหตุผลบังคับ + `COD_MISMATCH`; เงินสดที่เก็บเข้าบัญชีเงินสดในมือคนขับ (05) ต้องเคลียร์ตอน M16
- **DRV-163** distanceFromStopM > geofenceWarnKm → เหตุผลบังคับ ไม่บล็อก (E4)
- **DRV-164** หลังกดยืนยัน POD แก้ไม่ได้จากแอป; แก้ได้เฉพาะในเว็บโดย dispatcher (เก็บเวอร์ชันเดิม + เหตุผล)
- **DRV-165** server รับ POD แล้วส่งตรวจ AI (08) แบบ async ถ้าเปิด; ผลผิดปกติ → `POD_MISMATCH` (D5: AI ไม่แก้ข้อมูล POD เอง)
- **DRV-166** รูปทุกใบประทับเวลา+พิกัดใน metadata (ไม่ใส่ลายน้ำทับภาพ) [PROPOSED]; ไม่อนุญาตเลือกรูปจากคลังภาพ เว้นแต่ tenant เปิด (ค่าเริ่มต้นปิด เพื่อกันรูปเก่า)

**6. สถานะ** — stop → `completed | partial`; DO → `delivered | partially_delivered` (enum ใน 03/10)

**7. Event** — `pod.submit` → webhook `shipment.delivered`, `pod.uploaded` (เมื่อไฟล์ครบ), `cod.collected`

**8. กรณีผิดปกติ** — ผู้รับไม่ยอมเซ็น → ถ่ายรูปใบส่งของ/บันทึกหมายเหตุ ถ้าลายเซ็นบังคับและไม่มีทางแทน → ใช้ M13 เหตุผล "ผู้รับไม่เซ็นเอกสาร" (reason master หมวด "ไม่เซ็นเอกสาร") · แอปปิดกลางคัน → ร่าง POD เก็บในเครื่อง เปิดกลับมาต่อได้ · รูปขึ้นไม่ครบ > 24 ชม. → `POD_INCOMPLETE`

**8. กรณีผิดปกติ** — รูปใบเสร็จเบลอ (AI ให้ confidence ต่ำ) → แนะนำถ่ายใหม่ แต่ไม่บล็อก · ไม่มีเที่ยว (ค่าใช้จ่ายทั่วไป) → อนุญาตเฉพาะประเภทที่ตั้ง "ไม่ผูกเที่ยว"

**9. เกณฑ์ตรวจรับ**
- Given ถ่ายใบเสร็จน้ำมันออนไลน์ Then ช่อง ลิตร ราคา ยอด ปั๊ม ถูกเติมพร้อมป้าย AI แนะนำ และยังไม่ถูกส่งจนกว่ากด "ส่ง"
- Given น้ำมัน 450 ลิตร ถังรถ 200 ลิตร Then ส่งไม่ได้ "ลิตรเกินความจุถัง"

**10. เฟส** — P0 (OCR ตาม 08 P0/P1)

## 21. DRV-M9 โปรไฟล์ · M10 สิทธิ์และ PDPA

**1. จุดประสงค์** — M9: ข้อมูลส่วนตัว สลิปค่าเที่ยว ใบขับขี่ ภาษา ออกจากระบบ · M10: ขอสิทธิ์ตำแหน่ง/กล้อง/แจ้งเตือน และแจ้งนโยบายข้อมูลส่วนบุคคล

**2. ผู้ใช้** — driver

**3. หน้าจอ**
- **M9** (tab): ชื่อ, บริษัท (สลับได้ถ้า > 1), รถประจำ; ใบขับขี่: เลขที่ (ปิดบางส่วน), ประเภท, วันหมดอายุ (≤ 60 วัน → ข้อความเตือนสีส้ม); สลิปค่าเที่ยว/ค่าจ้าง (รายการงวด → PDF จาก 05); คะแนนการขับเดือนนี้ (ถ้าเปิด 06 FLT-M, P2); ภาษา (segmented TH | EN | 中文); คิวส่งข้อมูล (→ M17); นโยบายความเป็นส่วนตัว (→ M10 แบบอ่าน); เวอร์ชันแอป; ปุ่ม "ออกจากระบบ" (สีแดงตัวอักษร ไม่ใช่ปุ่มหลัก)
- **M10** (ครั้งแรกหลัง login และเมื่อ notice เปลี่ยนเวอร์ชัน): ขั้น 1 ประกาศความเป็นส่วนตัว (ข้อมูลที่เก็บ: ชื่อ เบอร์ ใบขับขี่ ตำแหน่งระหว่างปฏิบัติงาน รูป POD/ตรวจรถ; วัตถุประสงค์; ฐานกฎหมาย; ระยะเวลาเก็บ; ผู้รับข้อมูล; สิทธิ์เจ้าของข้อมูล; ช่องทางติดต่อ DPO ของบริษัทขนส่ง) → ปุ่ม "รับทราบ"; ขั้น 2 อธิบายแล้วขอสิทธิ์ทีละตัว: ตำแหน่ง (ขณะใช้งาน → แล้วขอ "ตลอดเวลา" พร้อมเหตุผลตามข้อกำหนดของ store), กล้อง, แจ้งเตือน; แต่ละตัวแสดงผลที่เกิดถ้าไม่ให้

**4. ฟิลด์ — `PrivacyAcknowledgement`**: driverId, tenantId, noticeVersion, acknowledgedAt, deviceId, locale · `DevicePermissionState`: location (`denied|while_in_use|always`), camera, notifications, updatedAt (ส่งทุกซิงก์ ให้ dispatcher เห็นว่าทำไมไม่มีตำแหน่ง)

**5. กฎธุรกิจ**
- **DRV-240** ฐานกฎหมายของข้อมูลคนขับที่จำเป็นต่องาน (ชื่อ ใบขับขี่ ตำแหน่งระหว่างงาน รูป) = สัญญาจ้าง/ประโยชน์โดยชอบด้วยกฎหมาย ไม่ใช่ความยินยอม — M10 จึงเป็น "รับทราบ" ไม่ใช่ "ยินยอม" [FACT ฐานกฎหมาย: thai-tax-docs-research §5.4; การใช้กับ GPS tracking คนขับ = OPINION ต้องให้ที่ปรึกษายืนยัน → [OPEN] DRV-Q1]
- **DRV-241** บริษัทขนส่ง = ผู้ควบคุมข้อมูล, เรา = ผู้ประมวลผล; ข้อความ notice เป็น template ที่ tenant แก้ชื่อบริษัท/DPO/ระยะเวลาเก็บได้ (ตั้งค่า → แอปคนขับ) และเก็บเวอร์ชัน
- **DRV-242** เก็บตำแหน่งเฉพาะช่วงปฏิบัติงาน: ตั้งแต่ trip `in_progress` (หรือกด "เริ่มงาน" ถ้า tenant เปิดโหมดเข้างาน) จนเที่ยวสุดท้าย `closed`; นอกช่วงนี้แอปไม่ขอตำแหน่ง background และแสดงสถานะ "ไม่ได้ติดตามตำแหน่ง" ใน M9
- **DRV-243** ไม่ให้สิทธิ์ตำแหน่ง → ยังใช้แอปได้ แต่ปุ่ม "ถึงจุด" ต้องใส่เหตุผลทุกครั้ง และ dispatcher เห็นป้าย "คนขับปิดตำแหน่ง"; ไม่ให้กล้อง → ทำขั้นที่บังคับรูปไม่ได้ (state ข้อ 23)
- **DRV-244** เลขบัตรประชาชน/ใบขับขี่เก็บแบบเข้ารหัสระดับฟิลด์และแสดงปิดบางส่วนในแอป (11-nfr)
- **DRV-245** ภาษาเปลี่ยนทันทีไม่ต้อง restart และจำต่อเครื่อง+ผู้ใช้
- **DRV-246** ออกจากระบบ: ถ้ามีคิวค้าง → dialog "ยังมีข้อมูลรอส่ง N รายการ ออกจากระบบไม่ได้จนกว่าจะส่งครบ" + ปุ่ม "ส่งตอนนี้"; admin บังคับออกจากเว็บได้ (ข้อมูลค้างจะหาย — ต้องยืนยัน 2 ชั้น) — ออกสำเร็จ → ลบข้อมูลในเครื่องของ tenant นั้น

**6. สถานะ** — notice: ยังไม่รับทราบ → รับทราบ(version) → (เวอร์ชันใหม่) ต้องรับทราบใหม่

**7. Event** — `driver.privacy_acknowledged`, `driver.permission_changed`, `driver.logout`

**8. กรณีผิดปกติ** — notice เวอร์ชันใหม่ระหว่างเที่ยว → แสดงหลังจบเที่ยว ไม่ขัดงาน · ใบขับขี่หมดแล้ว → แถบแดงใน M9 + กฎห้ามจ่ายงาน (03/06)

**9. เกณฑ์ตรวจรับ**
- Given login ครั้งแรก Then ต้องผ่าน M10 ก่อนเห็น M2 และมี record noticeVersion

- Given คิวค้าง 2 รายการ When กดออกจากระบบ Then ไม่ให้ออก

**10. เฟส** — P0 (สลิปค่าเที่ยว ตาม 05, คะแนนการขับ P2)
