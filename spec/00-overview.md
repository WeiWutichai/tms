## 1. ผลิตภัณฑ์

TMS (Transport Management System) แบบ SaaS หลายบริษัทในระบบเดียว (multi-tenant) สำหรับ **บริษัทขนส่งทางบกในไทย ขนาด 10–200 คัน ที่มีทั้งรถบริษัทและรถร่วม**

- งานหลัก: รับงาน → วางแผน/จัดรถ → วิ่งงานและติดตาม → POD → วางบิล/รับชำระ → จ่ายรถร่วม
- งานเสริม: บริหารรถ (fleet), รายงาน, เชื่อมระบบ (connector, Open API, webhook, MCP), AI ช่วยงาน
- ขายแบบสมัครเอง (self-signup) มีแพ็กเกจ และมี Platform Console ให้ทีมเราดูแลลูกค้า

## 2. หลักการที่ห้ามย้อน [DECISION]

| # | หลักการ | ผลต่อการพัฒนา |
|---|---|---|
| D1 | **ใช้งานแบบ standalone ได้ครบเป็นค่าเริ่มต้น** — ไม่มี ERP ก็ออกเอกสารบัญชี/ภาษีได้เอง | โมดูลบัญชีต้องครบในตัว; connector เป็น optional |
| D2 | **เชื่อม ERP/โปรแกรมบัญชีได้หลายตัว** (Express, FlowAccount, KRS, PEAK, SAP B1, API ทั่วไป) — KRS เป็นแค่ตัวเลือกหนึ่ง | ห้าม hard-code ERP ใด; UI การเชื่อมต่อเรียงเป็นกลาง ค่าเริ่มต้น "ไม่เชื่อม" |
| D3 | **สถานะเอกสารแยกจากสถานะซิงก์** | เอกสารมี `status` ของตัวเอง และ `syncStatus` แยกต่อ connector |
| D4 | **ไม่ผูกสัญญายาว ไม่มีค่าปรับ และไม่ล็อกฟีเจอร์พื้นฐาน** (ePOD, วางบิล, เอกสารภาษี) ไว้แพ็กเกจสูง | entitlement ของฟีเจอร์พื้นฐาน = ทุกแพ็กเกจ |
| D5 | **AI เสนอ คนยืนยัน** — ผลจาก AI เป็น "ร่าง" เสมอ งานที่กระทบเงิน ภาษี การจ่ายงาน หรือการลบ ต้องมีคนยืนยัน | ทุกฟีเจอร์ AI/MCP ที่เขียนข้อมูลผ่านสถานะ draft/suggestion |
| D6 | **REST API, MCP, webhook และเอกสาร API ใช้ schema ชุดเดียว** (รวม custom fields ของ tenant) | generate จาก OpenAPI spec กลาง |
| D7 | **ไม่ลบข้อมูลลูกค้าเอง** — ยกเลิกแล้ว export ได้ตามระยะเก็บข้อมูล | soft delete + retention job |
| D8 | ราคา/โควตาทุกหน้า **อ่านจากข้อมูลแพ็กเกจชุดเดียว** (`Plan/PlanVersion`) | ห้ามพิมพ์ราคาไว้ในหน้าใด |

## 3. ผู้ใช้และ role

### 3.1 ฝั่งลูกค้า (tenant)
| Role | หน้าที่หลัก | ค่าเริ่มต้นสิทธิ์ |
|---|---|---|
| ผู้ดูแลระบบ (owner/admin) | ตั้งค่าบริษัท ผู้ใช้ แพ็กเกจ การเชื่อมต่อ | ทุกอย่าง |
| ผู้จัดการ (manager) | อนุมัติ, override กฎห้ามจ่ายงาน, ดูรายงาน | ทุกอย่างยกเว้นแพ็กเกจ/ผู้ใช้ |
| ผู้วางแผน/จัดรถ (dispatcher) | SO, DO, กระดานวางแผน, จ่ายงานรถร่วม, ติดตาม, ข้อยกเว้น | ปฏิบัติการ + อ่านข้อมูลหลัก |
| บัญชี (accounting) | วางบิล, ใบกำกับ, รับชำระ, settlement, เงินเบิก | บัญชี + อ่านปฏิบัติการ |
| ช่าง/ฝ่ายรถ (fleet) | ใบสั่งซ่อม, PM, ยาง, อะไหล่, เอกสารรถ | fleet |
| ผู้อนุมัติ (approver) | อนุมัติเอกสาร/ใบสั่งซ่อมตามวงเงิน | อ่าน + อนุมัติ |
| นักพัฒนา (developer) | Open API, webhook, mapping, MCP | ตั้งค่านักพัฒนา |
| ดูอย่างเดียว (viewer) | ดู | อ่าน |
| คนขับ (driver) | แอปคนขับเท่านั้น | งานของตัวเอง |
| รถร่วม (subcontractor) | หน้ารถร่วมผ่านลิงก์/LINE | งานที่เสนอให้ตัวเอง |
| ผู้ส่งสินค้า/ผู้รับ (shipper/consignee) | หน้าติดตามผู้รับ (สาธารณะผ่านลิงก์), API key แบบจำกัด | งานของตัวเอง |

- ผู้ใช้หนึ่งคนอยู่ได้หลายบริษัท (membership) และมี role ต่างกันในแต่ละบริษัท
- สิทธิ์ละเอียดระดับ "โมดูล × การกระทำ" (ดู/สร้าง/แก้/ลบ/อนุมัติ/export) ตั้งได้ในหน้าสิทธิ์ตามบทบาท

## 4. คำศัพท์

| คำ | ความหมาย |
|---|---|
| Tenant | บริษัทลูกค้า 1 ราย (นิติบุคคล + สาขา) ข้อมูลแยกขาดจากรายอื่น |
| SO (ใบสั่งขนส่ง) | คำสั่งจากลูกค้า 1 งาน มีจุดรับ-ส่ง สินค้า ราคา |
| DO (ใบส่งของ) | เอกสารส่งมอบต่อจุดส่ง ใช้เก็บ POD และเป็นฐานวางบิล |
| เที่ยวรถ / ใบคุมรถ (Trip) | การวิ่งของรถ 1 คัน + คนขับ ในช่วงเวลาหนึ่ง มีหลาย stop และหลาย DO |
| Stop | จุดรับหรือจุดส่งในเที่ยว |
| POD | หลักฐานการส่งมอบ: รูป ลายเซ็น ชื่อผู้รับ เวลา พิกัด หรือรูปใบส่งของกระดาษที่เซ็นแล้ว |
| รถร่วม (subcontractor) | ผู้รับเหมาภายนอกพร้อมรถ รับงานผ่านหน้ารถร่วม/LINE |
| Settlement รถร่วม | การสรุปยอดค่าจ้างรถร่วมเพื่อจ่าย (หัก ณ ที่จ่าย 1%) |
| รถ active | รถที่ปิดงานอย่างน้อย 1 เที่ยวในเดือน (นิยามคิดเงิน — ดู 01-platform) |
| Connector | ตัวเชื่อมกับโปรแกรมบัญชี/ERP ที่เราเขียนให้ |
| Open API | REST API ให้ลูกค้า/คู่ค้าเชื่อมเอง |
| MCP | Model Context Protocol — ให้ AI assistant เรียกใช้ TMS |
| Custom field | ฟิลด์ที่ tenant เพิ่มเองต่อ entity |
| Exception | เหตุผิดปกติที่ต้องมีคนจัดการ (ล่าช้า, POD ไม่ครบ ฯลฯ) |

## 5. รูปแบบการเขียนข้อกำหนดในแต่ละโมดูล

ทุก feature ใช้หัวข้อเดียวกัน:

1. **จุดประสงค์** — 1–2 บรรทัด
2. **ผู้ใช้/สิทธิ์** — role ที่ใช้, การกระทำที่ต้องมีสิทธิ์
3. **หน้าจอ** — รายการหน้า, ส่วนประกอบหลัก (KPI, แท็บ, ตาราง, drawer, ฟอร์ม)
4. **ฟิลด์** — ตาราง: ชื่อ · ชนิด · บังคับ · กฎตรวจ · หมายเหตุ
5. **กฎธุรกิจ** — รหัส `XXX-nnn` ทีละข้อ
6. **สถานะ** — enum + ตารางการเปลี่ยนสถานะ (จาก → ไป · เงื่อนไข · ใครทำ · ผลข้างเคียง)
7. **การแจ้งเตือน / event** — event ที่เกิด (ใช้กับ webhook/audit)
8. **กรณีผิดปกติ** — error, ข้อมูลไม่ครบ, ออฟไลน์, ชนกัน
9. **เกณฑ์ตรวจรับ** — Given/When/Then สั้น ๆ
10. **เฟส** — P0/P1/P2

## 6. รูปแบบ UI ที่ใช้ร่วม (จาก design system ในต้นแบบ)

- Layout: sidebar ซ้าย (กลุ่มเมนูพับได้, ตัวนับ), top bar (breadcrumb, สลับภาษา TH/EN/中文, แจ้งเตือน, สร้างด่วน)
- หน้ารายการ: KPI card (คลิกกรอง) → แท็บสถานะ → ตารางมีตัวกรองใต้หัวคอลัมน์ + เมนูคอลัมน์ + แบ่งหน้า → drawer รายละเอียด
- Drawer มาตรฐาน: หัว 3 บรรทัด (ประเภท / เลข + สถานะ / คู่ค้า + เลขอ้างอิง) + เมนู ⋯ (แก้ไข · คัดลอกเป็นใบใหม่ · พิมพ์ · ยกเลิก) · แท็บ (สรุป / รายการ / เอกสารแนบ / กิจกรรม) · footer ติดล่าง
- การยกเลิก/override/อนุมัติ ต้องใส่เหตุผล (≥ 10 ตัวอักษร) และบันทึก audit
- ตัวเลขเงินทศนิยม 2 ตำแหน่ง, tabular-nums; วันที่ พ.ศ. ในโหมดไทย ค.ศ. ในโหมด EN/中文
- Design tokens: ดู `research/design-briefs.md` (สี, ฟอนต์ IBM Plex Sans Thai Looped, Sarabun สำหรับ A4)
