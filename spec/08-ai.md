5. **กฎธุรกิจ**
- **AI-010** ทุก prompt + output schema มีเวอร์ชัน (`promptVersion`) เก็บใน repo; เปลี่ยนเวอร์ชันต้องผ่านชุดทดสอบภาษาไทย (AI-016) ก่อน deploy
- **AI-011** [PROPOSED] เลือกรุ่นตามงาน (ต้องวัดกับข้อมูลไทยก่อนตัดสิน — ai-mcp-plan §3):

| งาน | ขนาดรุ่น | ตัวอย่างตระกูล |
|---|---|---|
| คัดแยกข้อความในกล่องรับงาน (งาน/ไม่ใช่งาน), จัดหมวด | เล็ก เร็ว | Claude Haiku |
| ดึงข้อมูลจากข้อความ/เอกสาร/รูป (order intake, OCR, POD) | กลาง รองรับภาพ | Claude Sonnet |
| ถามข้อมูล (วางแผนการเรียกเครื่องมือหลายขั้น), งานวิเคราะห์ระยะ 2–3 | ใหญ่ | Claude Opus |

  โมดูลต้องสลับผู้ให้บริการ/รุ่นได้ด้วย config ต่อ feature (`AiModelRoute(feature, provider, modelId, fallbackModelId)`)
- **AI-012** บังคับ structured output (JSON schema); output ไม่ผ่าน schema → retry 1 ครั้ง → ล้มเหลวคืน error `ai_unavailable` (ไม่หัก credit)
- **AI-013** ใช้ prompt caching สำหรับส่วนคงที่ (คำสั่งระบบ, schema, รายการลูกค้า/สถานที่ย่อ) เพื่อลดต้นทุน
- **AI-014** timeout 60 วิ (เอกสารหลายหน้า → async job + แจ้งเมื่อเสร็จ); ผู้ให้บริการล่ม → circuit breaker 5 นาที, ฟีเจอร์ AI แสดง "AI ไม่พร้อมใช้งานชั่วคราว" งานด้วยมือไม่กระทบ
- **AI-015** ข้อมูลอ้างอิงที่ส่งเข้า AI (รายชื่อลูกค้า สถานที่ สินค้า) ส่งเท่าที่จำเป็น: ค้นผู้สมัครก่อนด้วย search ภายใน (top 20) แล้วให้ AI เลือก — ไม่ส่ง master ทั้งหมด
- **AI-016** [PROPOSED] ชุดทดสอบภาษาไทย 200–500 ตัวอย่างต่อฟีเจอร์ (ข้อความ LINE, ใบเสร็จน้ำมัน, ใบแจ้งหนี้อู่, เอกสารรถ, รูป POD — ได้รับอนุญาตจากเจ้าของข้อมูล, ปิดบัง PII) — เกณฑ์เปิดฟีเจอร์: ความแม่นระดับฟิลด์ ≥ 90% สำหรับฟิลด์บังคับ [OPEN: เกณฑ์จริง]
- **AI-017** ข้อมูลส่วนบุคคล/PDPA:
  - [FACT] การส่งข้อมูลส่วนบุคคลไปประมวลผลนอกประเทศอยู่ภายใต้ พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล 2562 (หมวดการส่งข้อมูลไปต่างประเทศ ม.28–29) → [OPEN] ฝ่ายกฎหมายยืนยันกลไก (สัญญากับผู้ให้บริการ/ข้อความแจ้งลูกค้า) และลูกค้าองค์กรที่ห้ามส่งออกนอกประเทศ
  - [PROPOSED] ใช้ผู้ให้บริการแบบไม่นำข้อมูลไปฝึกโมเดล และเลือกตัวเลือกไม่เก็บข้อมูล/เก็บสั้นที่สุดเท่าที่ผู้ให้บริการมี
  - toggle "ปิดบังข้อมูลส่วนบุคคลก่อนส่ง" (ค่าเริ่ม เปิด): แทนเลขบัตรประชาชน 13 หลัก (ที่ไม่ใช่เลขนิติบุคคล), เบอร์โทร, เลขบัญชีธนาคาร ด้วย token ก่อนส่ง แล้วแทนกลับใน output — ข้อยกเว้น: ฟิลด์ที่ต้องการให้ AI อ่าน (เลขผู้เสียภาษีผู้ขายในใบเสร็จ) ส่งได้
  - ต้นฉบับ (ข้อความ/ไฟล์) เก็บใน storage ของ TMS ตามระยะเก็บข้อมูลปฏิบัติการ (01 PLT-016); prompt/response ดิบเก็บ 30 วันเพื่อ debug แล้วลบ [PROPOSED]
- **AI-018** ทุกการเรียกบันทึก ApiRequestLog-like trace (`AiTrace`: requestId, feature, modelId, promptVersion, tokens, latency, error) — ไม่เก็บเนื้อหาเกิน AI-017

## 2. สร้าง SO จากข้อความ/ไฟล์ (Order intake)

1. **จุดประสงค์** — ลดการพิมพ์ซ้ำเมื่อลูกค้าสั่งงานผ่าน LINE/อีเมล/PDF/Excel/รูปใบสั่งงาน
2. **ผู้ใช้/สิทธิ์** — ผู้มีสิทธิ์สร้าง SO (dispatcher, manager, owner/admin); feature `ai.enabled` + ตั้งค่า "รับงาน" เปิด
3. **หน้าจอ**
   - ปุ่มรองข้าง "+ สร้าง SO": **"สร้างจากข้อความ/ไฟล์"** (หน้า SO และทางลัดบนภาพรวม) และจากกล่องรับงาน (§3)
   - dialog ขั้น 1: แท็บ วางข้อความ / อัปโหลดไฟล์ (PDF, XLSX/CSV, JPG/PNG/HEIC; ลากวาง; หลายไฟล์ ≤ 5) / เลือกจากกล่องรับงาน → ปุ่ม "อ่าน" (แสดง credit ที่จะใช้)
   - ผลลัพธ์ **แบ่งจอ**: ซ้าย = ต้นฉบับ (ข้อความไฮไลต์ส่วนที่ถูกดึง สีต่อฟิลด์; PDF/รูปมีกรอบตรงตำแหน่ง; คลิกฟิลด์ขวา → เลื่อน/กะพริบไปที่แหล่ง) · ขวา = ฟอร์ม SO มาตรฐาน (รวม custom fields) ที่เติมแล้ว
   - ฟิลด์ความมั่นใจ **กลาง/ต่ำ: ขอบส้ม** + tooltip เหตุผล; ฟิลด์ที่หาไม่พบ: ว่าง + ข้อความเทา **"ไม่พบในต้นฉบับ"**; ฟิลด์จับคู่ master: แสดงค่าที่จับคู่ + ปุ่มเปลี่ยน + ตัวเลือกอื่น 2 อันดับ
   - ข้อความเดียวมีหลายงาน → แถบบนแสดง **"พบ {n} งาน"** + แท็บ SO ร่าง 1…n; ปุ่ม "สร้างใบนี้" / "สร้างทั้งหมด {n} ใบ" (เฉพาะเมื่อทุกใบไม่มีฟิลด์บังคับว่าง) / "ลบใบนี้"
   - แถบล่าง: ยอมรับ (สร้าง SO) / ปฏิเสธ (เลือกเหตุผล) / อ่านใหม่

5. **กฎธุรกิจ**
- **AI-030** ผลลัพธ์คือ SO **ร่าง** (สถานะ `draft`, `source=ai_intake`, ลิงก์ AiSuggestion) — ไม่สร้าง DO/เที่ยว/จ่ายงาน; ราคาและ VAT คำนวณจาก rate card ตามกฎ 03/05 ไม่ใช่จาก AI (AI-009)
- **AI-031** ฟิลด์ความมั่นใจต่ำ (< 0.60) ต้องถูก "แตะ" (focus แล้วยืนยัน หรือแก้) ก่อนปุ่มยอมรับจะเปิด [PROPOSED]; กลาง = ขอบส้มแต่ไม่บังคับ
- **AI-032** "ไม่พบในต้นฉบับ" ใช้เมื่อ AI ไม่พบข้อมูลจริง — ห้ามเดาค่าเติม (เช่น ห้ามใส่วันนี้แทนวันที่ที่ไม่ได้ระบุ); ค่าเริ่มต้นจากตั้งค่าลูกค้า (เช่น จุดรับประจำ) เติมได้แต่ป้าย "ค่าเริ่มต้นของลูกค้า" ไม่ใช่ "AI แนะนำ"
- **AI-033** แยกหลายงานเมื่อข้อความมีหลายชุด จุดรับ-ส่ง/วันที่/สินค้า ที่แยกกันได้ชัด; ไม่แน่ใจ → 1 งาน + flag `multiple_orders` ให้ผู้ใช้แยกเอง (ปุ่ม "แยกเป็น 2 งาน")
- **AI-034** ไฟล์ Excel/CSV ที่เป็นตาราง > 20 แถว → แนะนำใช้ field mapping + นำเข้า (07 §11) แทน; AI อ่านได้สูงสุด 200 แถว/ครั้ง
- **AI-035** ตรวจซ้ำ: hash ข้อความ/ไฟล์เดียวกันที่อ่านแล้วใน 7 วัน → แสดงผลเดิม ไม่หัก credit ซ้ำ
- **AI-036** ยอมรับแล้ว: บันทึก `final` + `fieldOutcome`; ต้นฉบับแนบไปกับ SO ในแท็บเอกสารแนบ
6. **สถานะ** — ตาม AiSuggestion (§1.6); SO ที่สร้างเข้าสถานะเริ่มของ 03
7. **Event** — `ai.suggestion_created {feature: order_intake, orders: n}`, `order.created` (เมื่อยอมรับ — webhook 07)
8. **กรณีผิดปกติ** — ข้อความไม่ใช่งาน (ทักทาย, ถามราคา) → แสดง "ไม่พบงานขนส่งในข้อความนี้" + ปุ่ม "สร้างเองจากข้อความนี้"; ข้อความมีคำสั่งแปลก (AI-005) → แถบเตือนเหลืองบนผล; รูปเบลอ → `low_quality_image` แนะนำถ่ายใหม่; ลูกค้า 2 รายชื่อคล้ายกัน → แสดง 2 ตัวเลือก ความมั่นใจกลาง
9. **เกณฑ์ตรวจรับ**
- Given ข้อความ LINE จากลูกค้าที่ผูกแล้ว "พรุ่งนี้ 8 โมง รับปูน 24 ตัน ที่คลังอยุธยา ส่งโรงงานสระบุรี ขอรถพ่วง 1 คัน PO 45890" ส่งเมื่อ 4 พ.ย. 2569 15:00 When อ่าน Then ฟอร์มมี ลูกค้า=ผู้ส่ง, รับ 5 พ.ย. 2569 08:00, จุดรับ=สถานที่ "คลังอยุธยา", จุดส่ง=สถานที่ "โรงงานสระบุรี", สินค้าปูน 24 ตัน, ประเภทรถ=พ่วง ×1, PO=45890 และ "เวลาส่ง" แสดง "ไม่พบในต้นฉบับ"
- Given ข้อความมี 3 งาน When อ่าน Then แถบ "พบ 3 งาน" และกด "สร้างทั้งหมด" ได้ SO ร่าง 3 ใบ
- Given SO มี custom field `po_ref` (regex `^\d{5}$`) When AI เติม "45890" Then ผ่านกฎ และอยู่ใน section "ข้อมูลเพิ่มเติม"

## 3. กล่องรับงาน (Inbox)

1. **จุดประสงค์** — รวมคำสั่งงานที่เข้ามาจาก LINE OA, อีเมลรับงาน และ MCP ไว้ที่เดียวเพื่อตรวจและแปลงเป็น SO
2. **ผู้ใช้/สิทธิ์** — dispatcher, manager, owner/admin (ดู/จัดการ); การตั้งค่าช่องทาง: owner/admin
3. **หน้าจอ** — เมนู ปฏิบัติการ → กล่องรับงาน (ตัวนับ = รอตรวจ)
   - แท็บสถานะ: รอตรวจ · สร้าง SO แล้ว · ไม่ใช่งาน · (ทั้งหมด)
   - ตาราง: เวลาเข้า, ช่องทาง (ไอคอน LINE/อีเมล/MCP), ผู้ส่ง (ลูกค้าที่จับคู่ หรือ "ไม่รู้จัก"), ตัวอย่างข้อความ/ชื่อไฟล์, ผล AI ย่อ ("พบ 2 งาน · มั่นใจสูง"), ผู้รับผิดชอบ, ป้าย **"จาก MCP · {ชื่อผู้ใช้}"** สำหรับร่างจาก MCP
   - drawer: ข้อความ/ไฟล์ต้นฉบับ + ผลอ่าน (มุมมองเดียวกับ §2) + ปุ่ม เปิดเป็น SO / ไม่ใช่งาน / มอบหมาย / ตอบกลับ (LINE/อีเมล ข้อความสำเร็จรูป เช่น "รับงานแล้ว เลขที่ SO-…")
   - ตั้งค่า (ตั้งค่า → การแจ้งเตือน → ช่องทาง / หรือในหน้ากล่องรับงาน): เชื่อม LINE OA (channel credentials ของบริษัท), อีเมลรับงาน (ที่อยู่เฉพาะ tenant เช่น `orders+{slug}@in.<domain>` หรือ forward จากอีเมลบริษัท), ผูกผู้ส่งกับลูกค้า (LINE userId / อีเมล / โดเมน → ลูกค้า), อ่านอัตโนมัติเมื่อข้อความเข้า (เปิด/ปิด)
4. **ฟิลด์ `InboxItem`**

5. **กฎธุรกิจ**
- **AI-040** ข้อความเข้า → สร้าง InboxItem ทันที (ไม่ต้องรอ AI); ถ้า "อ่านอัตโนมัติ" เปิดและมี credit → คัดแยก (รุ่นเล็ก) → ถ้าเป็นงาน → order intake (§2) แบบ background
- **AI-041** ข้อความ LINE ต่อเนื่องจากผู้ส่งเดียวกันภายใน 3 นาที รวมเป็น InboxItem เดียว [PROPOSED] (คนมักพิมพ์แยกหลายบรรทัด/ส่งรูปตาม)
- **AI-042** ผู้ส่งไม่ผูกลูกค้า → "ไม่รู้จัก" + ปุ่ม "ผูกกับลูกค้า" (บันทึก SenderBinding สำหรับครั้งถัดไป)
- **AI-043** รายการจาก MCP tool ร่าง (`create_order`, `order_from_text` ฯลฯ — 07 INT-142) เข้ากล่องรับงานด้วย channel `mcp` พร้อม SO ร่างที่เติมแล้ว และป้าย "จาก MCP · {ชื่อผู้ใช้}"
- **AI-044** "ไม่ใช่งาน" ต้องเลือกเหตุผล (สอบถาม / ซ้ำ / สแปม / อื่น ๆ); ผล AI ที่ถูกตั้งเป็นไม่ใช่งานนับเป็น rejected ของการคัดแยก
- **AI-045** ข้อความ LINE ที่เข้ามาเก็บตาม retention ปฏิบัติการ; บริษัทต้องแจ้งลูกค้าของตนเองเรื่องการใช้ข้อความ (Privacy Notice ของบริษัท — ลูกค้าเรารับผิดชอบ) [OPEN: ข้อความแนะนำ/เงื่อนไขที่ต้องมีใน Terms]
- **AI-046** การเชื่อม LINE OA ใช้ช่องทางของบริษัทลูกค้าเอง (ไม่ใช่ OA กลางของเรา); ค่าใช้จ่ายข้อความตอบกลับเป็นของ OA นั้น [PROPOSED]
6. **สถานะ InboxItem**

| จาก → ไป | เงื่อนไข | ใครทำ |
|---|---|---|
| (ใหม่) → `new` | ข้อความเข้า | ระบบ |
| `new` → `processing` → `ready` | AI อ่านเสร็จ | ระบบ |
| `new`/`ready` → `in_review` | ผู้ใช้เปิด/มอบหมาย | ผู้ใช้ |
| `ready`/`in_review` → `converted` | สร้าง SO ≥ 1 ใบ (สร้างบางใบได้ — เหลือใบร่างยังค้าง = `partially_converted`) | ผู้ใช้ |
| `ready`/`in_review` → `dismissed` | ไม่ใช่งาน + เหตุผล | ผู้ใช้ |
| `dismissed` → `in_review` | เรียกคืน | ผู้ใช้ |

   แท็บ "รอตรวจ" = `new` `processing` `ready` `in_review` `partially_converted`
7. **Event** — `inbox.item_received`, `inbox.item_converted`, `inbox.item_dismissed`; แจ้งเตือนในแอปถึง dispatcher เมื่อมีงานใหม่ (ตั้งได้ — 01 §13.5)
8. **กรณีผิดปกติ** — LINE webhook ซ้ำ → dedupe ด้วย externalMessageId; อีเมลมีลายเซ็น/ประวัติตอบกลับยาว → ตัด quoted text ก่อนส่ง AI; ไฟล์แนบเป็นไวรัส/ชนิดไม่รองรับ → ไม่ส่ง AI แสดงคำเตือน; credit หมด → InboxItem ยัง `new` ทำด้วยมือได้
9. **เกณฑ์ตรวจรับ** — Given LINE OA เชื่อมแล้ว When ลูกค้าส่งข้อความ + รูปใบสั่งงานภายใน 1 นาที Then เกิด InboxItem เดียว สถานะ `ready` ภายใน 30 วิ พร้อมผลอ่าน
10. **เฟส** — P1 (อีเมล + อัปโหลด + MCP) · LINE OA P1 [PROPOSED; ต้องทดสอบ LINE Messaging API ก่อน]

## 5. ตรวจ POD

1. **จุดประสงค์** — ตรวจหลักฐานส่งมอบให้ครบก่อนวางบิล ลดการถูกลูกค้าตีกลับ
2. **ผู้ใช้/สิทธิ์** — ระบบรันอัตโนมัติเมื่อ POD เข้า (ถ้าเปิด); dispatcher/accounting ดูผลและยืนยัน; การ override ต้องมีสิทธิ์แก้ POD/DO
3. **หน้าจอ**
   - drawer DO → แท็บ POD: รูป/ลายเซ็น/ใบส่งของกระดาษ + **ผลตรวจ AI เป็น checklist** (ไอคอน ✓ / ⚠ / ✗ + ข้อความ + ลิงก์ไปกรอบบนรูป) เช่น "รูปชัด ✓", "มีลายเซ็น ✓", "ชื่อผู้รับตรง ✓", "จำนวนตรงกับ DO ⚠ (ใบส่งของเขียน 118 ถุง DO 120 ถุง)", "เห็นความเสียหาย ✗" → สรุปบนสุด: **ผ่าน / ต้องตรวจ / ไม่ผ่าน**; ปุ่ม "ยืนยัน POD ด้วยตนเอง" (override + เหตุผล), "ขอ POD ใหม่จากคนขับ", "เปิดข้อยกเว้น"
   - หน้าวางบิล (05): ตัวกรอง **"POD ผ่าน AI แล้ว"** และคอลัมน์ผลตรวจ POD
   - รายการ DO: คอลัมน์/ตัวกรองผลตรวจ POD
4. **ฟิลด์ `PodCheck`**

| ฟิลด์ | ชนิด | หมายเหตุ |
|---|---|---|
| shipmentId, podId, suggestionId | | |
| items | json[] `{code, result pass|warn|fail|na, detail, sourceRef}` | |
| overall | `passed` `needs_review` `failed` | |
| confirmedBy, confirmedAt, overrideReason | | การยืนยัน/override ของคน |
| finalStatus | `ai_passed` `human_confirmed` `rejected` `pending` | ใช้กับตัวกรองวางบิล |

**รายการตรวจ** (ตั้งได้ว่าใช้ข้อใด — §8)

| code | ตรวจอะไร | วิธี | ไม่ผ่าน = |
|---|---|---|---|
| `image_quality` | รูปชัด อ่านได้ ไม่มืด/เบลอ | AI | warn |
| `signature_present` | มีลายเซ็นผู้รับ (ดิจิทัล หรือบนใบส่งของกระดาษ) | AI + ข้อมูลแอป | fail |
| `receiver_name` | ชื่อผู้รับที่กรอก/เขียนตรงกับผู้ติดต่อปลายทางหรือรายชื่อที่อนุญาต | AI + fuzzy match | warn |
| `quantity_match` | จำนวนบนใบส่งของ/ที่คนขับกรอก = จำนวนใน DO | AI อ่าน + เทียบ | warn (ต่าง ≤ เกณฑ์) / fail |
| `damage_visible` | เห็นความเสียหายของสินค้า/บรรจุภัณฑ์ | AI | fail |
| `doc_number_match` | เลข DO/อ้างอิงบนใบส่งของกระดาษตรงกับ DO | AI | warn |
| `stamp_present` | มีตราประทับบริษัทผู้รับ (เปิดต่อลูกค้า) | AI | warn |
| `location_time` | พิกัด/เวลา POD อยู่ใน geofence จุดส่งและหลังเวลาถึงจุด | กฎ (ไม่ใช้ AI) | warn |

5. **กฎธุรกิจ**
- **AI-060** รันเมื่อ POD ถูกส่งครบ (ออนไลน์แล้ว) — 1 ครั้งต่อชุด POD; POD ใหม่ (ขอส่งใหม่) → ตรวจใหม่
- **AI-061** overall: มี fail ≥ 1 → `failed`; มี warn ≥ 1 → `needs_review`; ไม่มี → `passed` (`finalStatus=ai_passed`)
- **AI-062** `failed` หรือ `quantity_match` ไม่ตรง → **สร้างข้อยกเว้นอัตโนมัติ** ประเภท "POD ไม่ครบ/ไม่ตรง" (04) พร้อมผลตรวจและลิงก์ DO — เป็นการแจ้งเตือน ไม่ใช่การแก้ข้อมูล (สอดคล้อง D5)
- **AI-063** ตัวกรอง "POD ผ่าน AI แล้ว" = `finalStatus ∈ {ai_passed, human_confirmed}`; การออกใบแจ้งหนี้ยังเป็นการกระทำของคน (05) — ผลตรวจ AI **ไม่บล็อก** การวางบิล เว้นแต่ลูกค้าตั้ง "ต้องมี POD ผ่าน" (05) ซึ่งคนยืนยันด้วยตนเองแทนได้
- **AI-064** "ยืนยัน POD ด้วยตนเอง" ต้องมีเหตุผล ≥ 10 ตัว → `human_confirmed` + ปิดข้อยกเว้นที่เกี่ยวข้อง (ถ้าผู้ใช้เลือก) + audit
- **AI-065** "ขอ POD ใหม่จากคนขับ" ส่งแจ้งเตือน M18 พร้อมเหตุผลจากรายการที่ไม่ผ่าน (04); รถร่วม → ผ่านหน้ารถร่วม/LINE
- **AI-066** เกณฑ์จำนวนต่าง (`quantity_match`) ตั้งต่อลูกค้า: ต่าง 0 = pass; ≤ x% = warn; > x% = fail [PROPOSED ค่าเริ่ม x = 2%]
- **AI-067** credit หมด/AI ปิด → `finalStatus=pending` และ checklist แสดง "ยังไม่ได้ตรวจด้วย AI"; กฎ `location_time` ยังทำงาน
6. **สถานะ PodCheck.finalStatus**

| จาก → ไป | เงื่อนไข | ใครทำ | ผลข้างเคียง |
|---|---|---|---|
| (ใหม่) → `pending` | POD ครบ | ระบบ | คิวตรวจ |
| `pending` → `ai_passed` | overall passed | ระบบ | event `pod.verified` |
| `pending` → `pending` (overall needs_review/failed) | | ระบบ | AI-062 |
| `pending` → `human_confirmed` | ยืนยันด้วยตนเอง + เหตุผล | ผู้ใช้ | `pod.verified {by: human}` |
| `pending` → `rejected` | ผู้ใช้ปฏิเสธ POD + ขอใหม่ | ผู้ใช้ | AI-065 |
| `rejected` → `pending` | POD ใหม่เข้ามา | ระบบ | ตรวจใหม่ |

7. **Event** — `pod.verified {shipmentId, result, by: ai|human}` (webhook สาธารณะ — 07), `exception.created` (ประเภท pod_mismatch)
8. **กรณีผิดปกติ** — POD ไม่มีรูปเลย (ตั้งค่าไม่บังคับรูป) → ตรวจเฉพาะ `location_time` + ข้อมูลที่กรอก; ภาพหลายหน้า > 6 → ตรวจ 6 รูปแรกที่ AI เลือกว่าเกี่ยวข้อง + แจ้ง; ลายเซ็นดิจิทัลว่าง (เส้นสั้นมาก) → warn
9. **เกณฑ์ตรวจรับ**
- Given DO 120 ถุง ใบส่งของเขียน 118 ถุง When POD เข้า Then checklist `quantity_match` ⚠ ข้อความ "ใบส่งของเขียน 118 ถุง DO 120 ถุง" และมีข้อยกเว้น "POD ไม่ครบ/ไม่ตรง" ใหม่ 1 รายการ
- Given 10 DO ผ่าน AI และ 2 ต้องตรวจ When หน้าวางบิลกรอง "POD ผ่าน AI แล้ว" Then เห็น 10 รายการ
10. **เฟส** — P1

## 6. AI แนะนำการจับคู่ฟิลด์ (Mapping suggestion)

4. **ฟิลด์** — `AiSuggestion(feature=mapping_suggest, proposed = {rules: [{sourcePath, targetField, transforms[], confidence, reason}], newCustomFields: [{sourcePath, entity, type, labelI18n, apiKey, confidence}]})`
5. **กฎธุรกิจ**
- **AI-070** ทำงานหลัง "จับคู่อัตโนมัติ" แบบกฎ (07 INT-120) — AI เติมเฉพาะแถวที่กฎจับไม่ได้หรือเสนอ transform ที่ขาด; แถวที่ผู้ใช้ตั้งเองแล้วไม่ถูกทับ

- การสร้าง custom field ต้องผ่านโควตา `custom_fields.per_entity` (01) และผู้ใช้กดสร้างเอง (AI-001)

7. **Event** — `ai.suggestion_reviewed`

9. **เกณฑ์ตรวจรับ** — Given payload มี `"ship_dt":"05/11/2569"` และ `"consignee_tel":"0812345678"` When ให้ AI แนะนำ Then แถวแรกเสนอ → `pickupAt` + transform `date(buddhist)` และแถวสองเสนอ → ผู้ติดต่อปลายทาง + `phone_th`

## 7. ถามข้อมูลด้วยภาษาพูด (Ask data)

1. **จุดประสงค์** — ให้ผู้บริหาร/ผู้ใช้ถามคำถามธุรกิจได้โดยไม่ต้องรู้ว่ารายงานอยู่ที่ไหน
2. **ผู้ใช้/สิทธิ์** — ทุก role ที่มีสิทธิ์ดูรายงาน/ข้อมูลที่ถาม (คำตอบอยู่ภายใต้สิทธิ์ผู้ถาม); ฟีเจอร์เปิดใน §8
3. **หน้าจอ** — ช่องค้นหา ⌘K มีแท็บ **"ถาม AI"** (และแผงด้านขวาสำหรับถามต่อเนื่อง); คำถามแนะนำ ("กำไรลูกค้าสยามพลาสติกเดือนนี้", "รถคันไหนกินน้ำมันผิดปกติสัปดาห์นี้", "ลูกหนี้เกิน 60 วันมีใครบ้าง"); คำตอบ = ข้อความสั้น + ตาราง/กราฟเล็ก + ลิงก์ **"เปิดในรายงาน"** (พร้อมตัวกรองเดียวกัน) + บรรทัดแหล่ง/ช่วงข้อมูล (เช่น "จากเที่ยวรถ 1–3 พ.ย. 2569, 42 เที่ยว"); ปุ่ม 👍/👎 + "คัดลอกตาราง"
4. **ฟิลด์** — `AskSession(id, userId, locale, messages[], createdAt)`; ต่อคำตอบ: `toolCalls[] {tool, params, rowCount}`, `dataRange`, `answerText`, `feedback`
5. **กฎธุรกิจ**
- **AI-072** ตอบเป็นภาษาที่ผู้ใช้เลือกใน UI (TH/EN/中文) ไม่ว่าคำถามเป็นภาษาใด; วันที่ใช้ พ.ศ. ในโหมดไทย ค.ศ. ในโหมดอื่น (00 §6); เงิน 2 ตำแหน่ง
- **AI-073** [DECISION] **อ่านอย่างเดียว**: AI เรียกได้เฉพาะเครื่องมืออ่านชุดเดียวกับ MCP tool ระดับ "อ่าน" + API รายงาน (09) — ไม่มี tool เขียน/ร่าง และ **ไม่สร้าง SQL อิสระ** [PROPOSED]
- **AI-074** เครื่องมือทำงานด้วย principal ของผู้ถาม; ไม่มีสิทธิ์ → เครื่องมือคืน `permission_denied` และ AI ตอบ "คุณไม่มีสิทธิ์ดูข้อมูล {โมดูล}" ห้ามสรุปจากความรู้อื่น
- **AI-075** ทุกคำตอบที่มีตัวเลขต้องอ้างช่วงข้อมูลและแหล่ง (ชื่อรายงาน/entity + ช่วงวันที่ + จำนวนแถว); ตัวเลขมาจากผลเครื่องมือเท่านั้น (AI-009) — AI ห้ามคำนวณยอดเงินเอง ยกเว้นการเรียงลำดับ/เลือกแถว
- **AI-076** คำถามกำกวม (ไม่มีช่วงเวลา) → ใช้ค่าเริ่ม "เดือนนี้" และบอกในคำตอบ; ชื่อลูกค้า/รถกำกวม → ถามกลับพร้อมตัวเลือก
- **AI-077** คำถามที่ขอให้ "แก้/สร้าง/ยกเลิก" → ตอบว่าทำไม่ได้ในโหมดถามข้อมูล + ลิงก์ไปหน้าที่เกี่ยวข้อง
- **AI-078** ผลเครื่องมือจำกัด ≤ 200 แถวต่อการเรียก; ตารางในคำตอบ ≤ 20 แถว + "ดูทั้งหมดในรายงาน"
6. **สถานะ** — ไม่มี (session เก็บ 30 วัน)
7. **Event** — `ai.ask_answered {toolCalls, credits}` (ภายใน)
8. **กรณีผิดปกติ** — ไม่มีข้อมูลในช่วง → "ไม่พบข้อมูล {ช่วง}" ไม่แต่งตัวเลข; เครื่องมือ timeout → ตอบบางส่วน + บอกว่าส่วนใดไม่ครบ; คำถามนอกเรื่อง TMS → ปฏิเสธสุภาพ
9. **เกณฑ์ตรวจรับ**
- Given ผู้ใช้ dispatcher (ไม่มีสิทธิ์รายงานกำไร) When ถาม "กำไรลูกค้าสยามพลาสติกเดือนนี้" Then ตอบว่าไม่มีสิทธิ์ และไม่มีตัวเลขกำไรในคำตอบ
- Given UI โหมด EN When ถามเป็นภาษาไทย "ลูกหนี้เกิน 60 วันมีใครบ้าง" Then คำตอบเป็นภาษาอังกฤษ วันที่ ค.ศ. มีตารางลูกค้า + ยอด + บรรทัดแหล่งข้อมูล และลิงก์รายงานอายุลูกหนี้
10. **เฟส** — P1 (ชุดเครื่องมืออ่าน ~15 ตัวตาม MCP อ่าน) · กราฟในคำตอบ P2

## 8. ตั้งค่า → AI และประวัติ AI

1. **จุดประสงค์** — ให้ลูกค้าควบคุมการใช้ AI, เห็น credit, ความเป็นส่วนตัว และความแม่น
2. **ผู้ใช้/สิทธิ์** — แก้: owner/admin; ดู: manager, developer (01 §12)
3. **หน้าจอ** — ตั้งค่า → AI
   - **สวิตช์**: เปิด/ปิด AI ทั้งบริษัท + รายฟีเจอร์ (รับงาน · อ่านอัตโนมัติในกล่องรับงาน · OCR · ตรวจ POD · แนะนำ mapping · ถามข้อมูล) ; ตรวจ POD: เลือกรายการตรวจ (§5) + เกณฑ์จำนวนต่างค่าเริ่ม
   - **AI credit เดือนนี้**: แถบใช้แล้ว/โควตา (+ add-on) แยกตามฟีเจอร์ (กราฟแท่ง) + ปุ่ม "ซื้อเพิ่ม" (ลิงก์หน้าแพ็กเกจ 01 §8) + ตาราง credit ต่อการใช้งาน (§1.3)
   - **ความเป็นส่วนตัว**: คำอธิบายว่าข้อมูลส่งไปประมวลผลที่ใด (ผู้ให้บริการ, ภูมิภาค), ไม่ใช้ข้อมูลฝึกโมเดล, ระยะเก็บ; toggle "ปิดบังเลขบัตร/เบอร์โทร/เลขบัญชีก่อนส่ง" (ค่าเริ่มเปิด)
   - **ประวัติ AI**: ตาราง ฟีเจอร์ / เอกสาร (ลิงก์ต้นฉบับ) / ผล (รับ · แก้แล้วรับ · ปฏิเสธ · รอ) / ผู้ยืนยัน / เวลา / credit; ตัวกรอง; drawer แสดงค่า AI vs ค่าสุดท้ายต่อฟิลด์
   - **ความแม่น 30 วัน** ต่อฟีเจอร์: % รับโดยไม่แก้, % ฟิลด์ถูก, ฟิลด์ที่ถูกแก้บ่อย 5 อันดับ
4. **ฟิลด์** — `TenantAiSettings(enabled, features{key: bool}, autoReadInbox, maskPii, podChecks[], podQuantityTolerancePct, updatedBy)`
5. **กฎธุรกิจ**
- **AI-080** ความแม่นระดับฟิลด์ = ฟิลด์ที่ `fieldOutcome=accepted` ÷ ฟิลด์ที่ AI เสนอ (ไม่นับ `not_found` ที่ผู้ใช้เติมเอง แยกเป็น "หาไม่พบ %"); คำนวณเฉพาะ suggestion ที่ถูกตัดสินแล้ว
- **AI-081** ปิดฟีเจอร์มีผลทันที; suggestion ที่ `pending` อยู่ยังตรวจ/ยอมรับได้
- **AI-082** ทีมเราปิด AI ของ tenant (01 PLT-115) → หน้านี้แสดง "AI ถูกปิดโดยผู้ให้บริการ" + เหตุผลที่เปิดเผยได้ สวิตช์ล็อก
- **AI-083** ข้อมูลการใช้/ต้นทุนส่งไป Console (01 §10.7) ราย tenant: credit, จำนวนเรียกต่อฟีเจอร์, ต้นทุนผู้ให้บริการ, error rate
6. **สถานะ** — ไม่มี
7. **Event** — `ai.settings_changed` (audit)
9. **เกณฑ์ตรวจรับ** — Given ปิด "ตรวจ POD" When POD ใหม่เข้า Then ไม่มี PodCheck จาก AI (มีเฉพาะกฎ location_time) และไม่หัก credit · Given 10 suggestion order intake ยอมรับ 7 (แก้ 2) ปฏิเสธ 1 รอ 2 Then ประวัติแสดงครบ 10 และความแม่นคำนวณจาก 8 รายการ
10. **เฟส** — P1
