# 03 — แผนทดสอบ เฟส 0

> ร่าง 10 พ.ย. 2569 · อ้างอิง `spec/11-nfr.md` (กลยุทธ์ทดสอบ), `docs/01` §4 (state machine), `docs/04` F (กฎภาษี)

## 1. เป้าหมาย

เฟส 0 ผ่านเมื่อ (docs/02 §7): (1) KRS ปิดงวด 2 เดือนติดกันโดย MISMATCH ค้าง = 0 และ (2) tenant standalone ออกใบกำกับภาษี + 50 ทวิ ครบ 1 รอบเดือนโดยนักบัญชีของเขายอมรับ การทดสอบทั้งหมดออกแบบเพื่อให้สองข้อนี้ผ่านได้โดยไม่มีเรื่องเซอร์ไพรส์ตอนนำร่อง

## 2. ระดับการทดสอบ

| ระดับ | ทดสอบอะไร | รันเมื่อ | เกณฑ์ |
|---|---|---|---|
| Unit | `packages/domain`: pricing, VAT/WHT, ปัดเศษ, state machine, เลขเอกสาร | ทุก PR | ครอบคลุม ≥ 90% ของ `domain` |
| Integration (API + PostgreSQL จริง) | endpoint ทุกตัว: สิทธิ์, validation, idempotency, ETag, pagination, error format | ทุก PR | ทุก endpoint มี happy path + อย่างน้อย 1 error path |
| Tenant isolation | ทุกตารางที่มี `tenant_id`: tenant A อ่าน/แก้ของ B ไม่ได้ (ผ่าน API และผ่าน SQL ด้วย role ของแอป) | ทุก PR | 100% ของตาราง; CI fail ถ้าตารางใหม่ไม่มี test |
| Contract | OpenAPI diff กับ main: ห้าม breaking change โดยไม่ตั้งใจ; client ที่ generate ต้อง build ผ่าน | ทุก PR | ไม่มี breaking ที่ไม่ได้ติดป้าย |
| E2E (เบราว์เซอร์) | เส้นทางหลัก 8 เส้น (§3) | ทุกคืน + ก่อน release | ผ่านทั้งหมด |
| PDF | เอกสาร 6 ชนิด + 50 ทวิ + ใบคุมรถ: ฟิลด์บังคับครบ, เทียบภาพกับต้นแบบที่เซ็นรับ | ทุกคืน | ไม่มีส่วนต่างที่ไม่ได้อนุมัติ |
| Connector | KrsAdapter กับ mock จาก contract: สำเร็จ, 409, 503, timeout, ส่งซ้ำ, reconcile | ทุก PR ที่แตะ integration | ทุก error class มี test |
| Performance | list API, กระดานวางแผน 200 คัน × 7 วัน, invoice run 500 DO | ปลาย ST5, ST9 | ตามเป้าใน `spec/11-nfr.md` |
| Security | รายการตรวจ OWASP ASVS L2 ส่วนที่เกี่ยว, dependency scan, secret scan | ทุก PR (scan) + ST9 (ตรวจมือ) | ไม่มี high/critical ค้าง |
| UAT | script ตามบทบาทจริง (§5) | ST9 + ช่วงนำร่อง | ผู้ใช้จริงเซ็นรับ |

## 3. เส้นทาง E2E หลัก

1. ตั้งค่าองค์กร → สาขา → เลขเอกสาร → นำเข้าลูกค้า/รถจาก Excel (dry-run แล้ว commit)
2. สร้าง order ด้วยมือ → ราคาจาก rate card → จัดรถบนกระดาน → dispatch → ใบคุมรถ PDF
3. จ่ายงานรถร่วมผ่านลิงก์ → รถร่วมรับงาน + ใส่ทะเบียน/คนขับ → ePOD ผ่านลิงก์ → ปิดงาน
4. ส่งไม่สำเร็จ / ส่งบางส่วน → actual quantity → งานส่งซ้ำ
5. คิวพร้อมวางบิล → draft → finalize → ใบแจ้งหนี้ + ใบวางบิล PDF
6. รับชำระ (หัก ณ ที่จ่าย 1% + แนบ 50 ทวิ) → ใบเสร็จ/ใบกำกับภาษีออกอัตโนมัติ → aging อัปเดต
7. ใบลดหนี้อ้างใบกำกับเดิม → รายงานภาษีขายแสดงถูก
8. Settlement รถร่วม → อนุมัติ (คนละคนกับผู้สร้าง) → 50 ทวิ PDF

เพิ่มเมื่อ ST8: order เข้าจาก KRS → วางบิล → push กลับ KRS → reconcile ไม่มี MISMATCH

## 4. Golden test ภาษี (สำคัญที่สุด)

- ทำชุดตัวอย่างเป็นไฟล์ข้อมูล (ไม่ใช่โค้ด): input = รายการบรรทัด + การตั้งค่าลูกค้า; expected = ฐานยกเว้น, ฐาน 7%, VAT, WHT, ยอดสุทธิ, ประเภทเอกสารที่ต้องออก
- ชุดเริ่มต้นอย่างน้อย 25 เคส:
  - ค่าขนส่งอย่างเดียว (ยกเว้น VAT) — ไม่มีใบกำกับภาษี
  - ค่าขนส่ง + ค่าขึ้นลง (7%) — ใบเดียวแยกบรรทัด และแบบ 2 เอกสาร
  - หัก ณ ที่จ่าย 1% / 3% ปนกัน; ยอดต่ำกว่า 1,000 บาท
  - รับชำระบางส่วน 2 งวด
  - ออกใบกำกับก่อนรับเงิน (`ON_ISSUE`) กับตอนรับเงิน (`ON_PAYMENT`)
  - ใบลดหนี้เต็มใบ / บางส่วน; ใบเพิ่มหนี้
  - ยกเลิกก่อนส่งลูกค้า; ใบแทน
  - Settlement รถร่วม: บุคคลธรรมดา / นิติบุคคล, มีรายการหัก (เงินเบิก, ค่าปรับ)
  - ปัดเศษ: ผลรวม VAT รายบรรทัดกับ VAT จากยอดรวมต่างกัน 0.01
- **นักบัญชีต้องเซ็นรับ expected ของทุกเคส** ก่อนปิด ST5 (เคสที่ขึ้นกับคำถามค้างใน `06-questions-accountant.md` ให้ติดป้ายรอคำตอบ)
- เมื่อคำตอบนักบัญชีเปลี่ยนกฎ → แก้ที่ไฟล์ golden ก่อน แล้วค่อยแก้โค้ด

## 5. UAT ตามบทบาท

| บทบาท | Script (ย่อ) | ผู้ทดสอบ |
|---|---|---|
| ผู้จัดรถ | รับ 20 งาน/วัน → จัดรถ → จ่ายรถร่วม 5 งาน → ติดตาม → ปิดงาน | dispatcher ของลูกค้านำร่อง |
| รถร่วม | เปิดลิงก์บนมือถือ → รับงาน → POD → ดูใบจ่าย | รถร่วมจริง 3 ราย |
| บัญชี | วางบิลรอบเดือน → รับชำระ → ใบกำกับ → ใบลดหนี้ 1 ใบ → settlement → 50 ทวิ → รายงานภาษีขาย | นักบัญชีของลูกค้า |
| ผู้ดูแล | เชิญผู้ใช้ → ตั้งสิทธิ์ → ดู audit → ระงับผู้ใช้ | เจ้าของ/แอดมิน |
| KRS | order เข้า → วางบิล → push → ตรวจใน KRS → reconcile → ปิดงวด | ทีมบัญชีฝั่ง KRS |

ทุก script มีแบบบันทึกผล: ผ่าน/ไม่ผ่าน, ปัญหา, ความรุนแรง (ขวางงาน / ทำงานได้แต่ลำบาก / เล็กน้อย)

## 6. เกณฑ์ปล่อยขึ้นใช้งานจริง (go-live)

- ไม่มีข้อบกพร่องระดับ "ขวางงาน" ค้าง; ระดับ "ลำบาก" มีทางเลี่ยงที่เขียนไว้
- golden test ภาษีเขียว 100% และนักบัญชีเซ็นรับ
- tenant isolation เขียว 100%
- ซ้อมกู้ข้อมูลจาก backup สำเร็จ 1 ครั้ง (จับเวลา)
- มี runbook: ระบบล่ม, connector ล้มเหลว, เลขเอกสารผิด, ลูกค้าขอลบข้อมูล

## 7. ข้อมูลทดสอบ

- seed tenant "ศรีไทยขนส่ง" (ชุดเดียวกับต้นแบบ) + tenant ที่สองสำหรับ isolation
- ห้ามใช้ข้อมูลจริงของลูกค้านอก production; สำเนาเพื่อ debug ต้องปิดบังชื่อ/เลขบัตร/เบอร์โทร
