# ชุดคำถามถึงทีม KRS ERP — การเชื่อมต่อ TMS กับ KRS

| | |
|---|---|
| **ถึง** | ทีมพัฒนาและทีมที่ปรึกษาบัญชีของ KRS ERP |
| **จาก** | ทีมพัฒนา TMS บริษัท Innovera |
| **วันที่จัดทำ** | 10 พฤศจิกายน 2569 (ฉบับที่ 1) |
| **จำนวนคำถาม** | 18 ข้อ (ส่วนที่ 1: 12 ข้อ · ส่วนที่ 2: 6 ข้อ) + รายการขอยืนยันความเข้าใจ 9 ข้อ |

## ระบบนี้คืออะไร

- TMS คือระบบบริหารงานขนส่งที่ใช้ผ่านเว็บและแอป สำหรับบริษัทรถบรรทุกไทยขนาด 10–200 คัน ทั้งรถของบริษัทเองและรถร่วม ทำงานตั้งแต่รับงาน จัดรถ ยืนยันการส่งของ จนถึงออกเอกสารเรียกเก็บเงินและจ่ายเงินรถร่วม
- TMS ออกเอกสารบัญชีและภาษีได้เองโดยไม่ต้องมีระบบบัญชี และเชื่อมกับระบบบัญชี/ERP ได้ผ่าน "ตัวเชื่อม" แยกตามแต่ละระบบ
- KRS เป็นระบบแรกที่เราจะทำตัวเชื่อมและทดลองใช้จริง (ลูกค้านำร่อง) ปัจจุบันเชื่อมผ่าน API ใบแจ้งหนี้ที่มีอยู่
- คำตอบของท่านกำหนดว่าตัวเชื่อม KRS ทำอะไรได้บ้าง สิ่งใดที่ KRS ไม่รองรับ TMS จะทำเองแล้วส่งข้อมูลเท่าที่ KRS รับได้

## ทำไมจึงถาม และต้องการคำตอบเมื่อไร

เรากำลังจะเริ่มพัฒนา และต้องกำหนดว่าเอกสารแต่ละประเภท "ระบบใดเป็นต้นทาง" ใครออกเลข และจะจัดการอย่างไรเมื่อเอกสารถูกแก้หลังลงบัญชีหรือหลังปิดงวด ถ้ากำหนดผิด ยอดบัญชีสองระบบจะไม่ตรงกัน

- **ส่วนที่ 1 (KRS-1 ถึง KRS-12):** ขอคำตอบ **ก่อนเริ่มออกแบบฐานข้อมูลบัญชี (สัปดาห์ที่ 2 ของโครงการ)**
- **ส่วนที่ 2 (KRS-13 ถึง KRS-18) และส่วนที่ 3:** ขอคำตอบ **ก่อนเปิดใช้งานจริงกับลูกค้านำร่อง**

## วิธีตอบ

- ตอบสั้น ๆ เป็นตัวอักษรตัวเลือก (A / B / …) ในบรรทัด "คำตอบ" ได้เลย ถ้าเป็นสิ่งที่ "ทำได้แต่ต้องพัฒนาเพิ่ม" โปรดระบุกำหนดการโดยประมาณ
- ถ้าคำตอบคือ "ทำไม่ได้" ก็เป็นคำตอบที่ใช้ได้ เรามีทางสำรองทุกข้อ (ดูบรรทัด "สิ่งที่เราจะทำถ้ายังไม่ได้คำตอบ") เพียงต้องรู้ก่อนเริ่มออกแบบ
- ตัวอย่างตัวเลขที่ใช้: งานหนึ่งงานมี **ค่าขนส่ง 10,000 บาท + ค่ายกขน 500 บาท**

## ส่วนที่ 1 — ต้องตอบก่อนเริ่มพัฒนา

### ก. ประเภทเอกสาร เจ้าของเอกสาร และเลขที่

**KRS-1 — KRS รับเอกสารประเภทใดจากระบบภายนอกได้บ้าง และเอกสารที่สร้างผ่าน `POST /invoice` คือเอกสารอะไรในระบบบัญชีของ KRS?**
- **บริบท:** TMS ออกเอกสาร 6 กลุ่ม คือ ใบแจ้งหนี้/ใบวางบิล, ใบเสร็จรับเงิน/ใบกำกับภาษี, ใบลดหนี้/ใบเพิ่มหนี้, การรับชำระ, ใบจ่ายเงินรถร่วม (เจ้าหนี้ พร้อมหัก ณ ที่จ่าย), ใบส่งของ (DO) ปัจจุบันเราทราบเพียง endpoint ใบขาย (เลข SA-S…)
- **ตัวเลือก:** ต่อประเภท — (A) รับผ่าน API ที่มีอยู่ (B) จะเปิด API ให้ — ภายในเมื่อใด (C) รับเป็นไฟล์นำเข้า (D) ไม่รับ ให้ฝ่ายบัญชีคีย์เอง
- **สิ่งที่เราจะทำถ้ายังไม่ได้คำตอบ:** ส่งเฉพาะใบแจ้งหนี้ผ่าน `POST /invoice` เอกสารอื่นออกและเก็บใน TMS แล้วส่งออกเป็นไฟล์ให้ฝ่ายบัญชี
- **ผลกระทบ:** กำหนดความสามารถของตัวเชื่อม KRS และตารางว่าเอกสารแต่ละประเภทระบบใดเป็นต้นทาง ประเภทที่ KRS ไม่รับ = TMS เป็นต้นทางและไม่ส่งข้อมูล
- **คำตอบ:** ใบแจ้งหนี้ ___ / ใบกำกับภาษี-ใบเสร็จ ___ / ใบลด-เพิ่มหนี้ ___ / รับชำระ ___ / ใบจ่ายรถร่วม ___ / DO ___

**KRS-2 — ใบกำกับภาษี/ใบเสร็จรับเงินที่ลูกค้าปลายทางได้รับ จะออกจากระบบใด — KRS (ตามที่ทำอยู่) หรือ TMS?**
- **บริบท:** ถ้าทั้งสองระบบออกใบกำกับภาษี จะมีเอกสารภาษีซ้ำสองชุดสำหรับรายการเดียวกัน จึงต้องเลือกระบบเดียวต่อบริษัท
- **ตัวเลือก:** (A) KRS ออก — TMS ออกเพียงใบแจ้งหนี้/ใบวางบิล และไม่แสดงเลขใบกำกับภาษี (B) TMS ออก — KRS รับเป็นข้อมูลเพื่อลงบัญชี ไม่ออกเลขใบกำกับภาษีซ้ำ (C) แยกตามบริษัท (NSF / PP) — โปรดระบุ
- **สิ่งที่เราจะทำถ้ายังไม่ได้คำตอบ:** แบบ A (ตามที่ใช้งานอยู่)
- **ผลกระทบ:** A → TMS ปิดการออกใบกำกับภาษีสำหรับบริษัทที่เชื่อม KRS / B → KRS ต้องรับเลขและวันที่ใบกำกับภาษีจาก TMS และต้องได้คำตอบข้อ KRS-4 และ KRS-5 เป็น "ได้"
- **คำตอบ:**

**KRS-3 — เลขที่เอกสาร: เลขที่พิมพ์บนเอกสารซึ่งลูกค้าถือ จะเป็นเลขของระบบใด?**
- **บริบท:** ปัจจุบัน KRS ออก `transactionNo` และ `voucherNo` (SA-S{YYMM}-{NNNN}) เอง และไม่รับเลขจากภายนอก ส่วน TMS ส่งเลขของตน (`tmsVoucherNo`) ไปเพื่อกันส่งซ้ำ ถ้าเอกสารต้องพิมพ์ทันทีที่ TMS แต่ต้องใช้เลขของ KRS TMS ต้องรอคำตอบจาก KRS ก่อนพิมพ์
- **ตัวเลือก:** (A) เลข KRS เป็นเลขทางการ — TMS แสดงเลขชั่วคราวจนได้ `voucherNo` กลับมา จึงพิมพ์และส่งลูกค้าได้ (B) เลข TMS เป็นเลขทางการ — KRS เก็บเลข TMS ในช่องอ้างอิงและแสดงบนเอกสาร/รายงาน (C) สองเลขคู่กัน: เลข TMS บนใบแจ้งหนี้ เลข KRS บนเอกสารภาษี
- **สิ่งที่เราจะทำถ้ายังไม่ได้คำตอบ:** แบบ C — TMS ออกเลขใบแจ้งหนี้ของตัวเองและพิมพ์ได้ทันที เก็บ `voucherNo` ของ KRS เป็นเลขอ้างอิง
- **ผลกระทบ:** A → เอกสารพิมพ์ไม่ได้ในช่วงที่ KRS ไม่ตอบ (เช่น 503) ต้องตกลงเวลาตอบสูงสุดและวิธีสำรอง / B → KRS ต้องเปิดให้รับเลขจากภายนอก (ปัจจุบันส่งมา = 400)
- **คำตอบ:**

**KRS-4 — ใบแจ้งหนี้ใบเดียวที่มีทั้ง "ค่าขนส่ง (ยกเว้น VAT)" และ "ค่าบริการ (VAT 7%)" — KRS รับได้หรือไม่?**
- **บริบท:** ตัวอย่าง ค่าขนส่ง 10,000 บาท (ยกเว้น) + ค่ายกขน 500 บาท (VAT 35) สัญญา API ปัจจุบันไม่มีฟิลด์ประเภท VAT ต่อรายการ และ KRS เป็นผู้คำนวณยอดเงินและส่วนลดเอง
- **ตัวเลือก:** (A) เพิ่มฟิลด์รหัส VAT ต่อรายการได้ (B) ไม่ได้ — ต้องแยกเป็น 2 ใบตามประเภท VAT (C) ใช้ `itemCode` หรือ `accountCode` เป็นตัวกำหนด VAT ฝั่ง KRS — โปรดให้รายการรหัส
- **สิ่งที่เราจะทำถ้ายังไม่ได้คำตอบ:** แบบ B — TMS แยกส่งเป็น 2 ใบ (ใบค่าขนส่งยกเว้น และใบค่าบริการ 7%)
- **ผลกระทบ:** A, C → ส่งใบเดียวได้ ต้องเพิ่มการจับคู่รหัส VAT / B → ใบแจ้งหนี้ 1 ใบใน TMS เท่ากับ 2 เอกสารใน KRS (การอ้างอิงและการเทียบยอดเป็น 1 ต่อ 2)
- **คำตอบ:**

### ข. การแก้ไข ยกเลิก และการลงบัญชี

**KRS-5 — ใบลดหนี้/ใบเพิ่มหนี้: KRS จะเปิด endpoint (เช่น `POST /creditnote`, `POST /debitnote`) ที่อ้าง `transactionNo` เดิมได้หรือไม่?**
- **บริบท:** หลักของ TMS คือเอกสารที่ออกแล้วแก้ไม่ได้ ต้องปรับด้วยใบลดหนี้/ใบเพิ่มหนี้ ปัจจุบัน KRS มีเพียง `PUT /invoice/{transactionNo}` ที่แทนที่ทั้งใบ เช่น ใบ 10,500 บาท ลดหนี้ 500 บาท เราต้อง PUT ใบยอด 10,000 บาททับ
- **ตัวเลือก:** (A) เปิด endpoint ใบลดหนี้/ใบเพิ่มหนี้ — ภายในเมื่อใด (B) ไม่เปิด — ใช้ PUT ทับต่อไป (C) ไม่เปิด — ฝ่ายบัญชีทำใบลดหนี้ใน KRS เอง โดย TMS ส่งรายการแจ้ง
- **สิ่งที่เราจะทำถ้ายังไม่ได้คำตอบ:** แบบ B — TMS ออกใบลดหนี้ของตัวเอง แล้วส่ง "ยอดหลังปรับ" ด้วย PUT ถ้าใบนั้นลงบัญชีแล้วหรือเก่ากว่าจำนวนวันที่ตกลงกัน ต้องให้ฝ่ายบัญชีอนุมัติก่อนส่ง
- **ผลกระทบ:** A → เอกสารสองระบบตรงกันแบบ 1 ต่อ 1 และเลิกใช้ PUT ทับ / B, C → เอกสารฝั่ง KRS ต่างรูปจาก TMS (ยอดสุทธิเท่ากัน) ต้องมีขั้นตอนอนุมัติและเทียบยอดเพิ่ม
- **คำตอบ:**

**KRS-6 — การยกเลิกใบที่ส่งเข้า KRS แล้ว (ปัจจุบันไม่มี `DELETE /invoice`) ให้ทำอย่างไร?**
- **บริบท:** เช่น ออกใบแจ้งหนี้ผิดลูกค้า ต้องยกเลิกทั้งใบใน TMS
- **ตัวเลือก:** (A) KRS เปิด endpoint ยกเลิก (เช่น `POST /invoice/{transactionNo}/void`) (B) PUT ให้รายการว่างหรือยอดศูนย์ (C) ฝ่ายบัญชียกเลิกใน KRS เอง โดย TMS แจ้งรายการที่ต้องยกเลิก (D) ทำใบลดหนี้เต็มใบ
- **สิ่งที่เราจะทำถ้ายังไม่ได้คำตอบ:** แบบ C — TMS ยกเลิกเอกสารของตัวเองทันที และขึ้นรายการ "รอยกเลิกใน KRS" ให้ฝ่ายบัญชีดำเนินการแล้วกดยืนยัน
- **ผลกระทบ:** A → ยกเลิกอัตโนมัติทั้งสองระบบ / B ถึง D → ต้องมีคิวงานที่ทำด้วยมือ และสถานะ "ยกเลิกแล้วใน TMS แต่ยังไม่ยกเลิกใน KRS"
- **คำตอบ:**

**KRS-7 — สถานะลงบัญชี (GL): ขอให้ `GET /invoice/{transactionNo}` บอกได้ว่าใบนั้นลง GL แล้วหรือยัง**
- **บริบท:** ใบที่มาจาก API ยังไม่ลง GL จนกว่าฝ่ายบัญชีเปิดใบและกดบันทึก แต่ TMS ไม่มีทางรู้ จึงไม่รู้ว่าการ PUT ทับปลอดภัยหรือไม่
- **ตัวเลือก:** (A) เพิ่มฟิลด์ใน GET เดิม — โปรดระบุชื่อและชนิด (เช่น `postedAt` เป็นวันเวลา หรือ `glStatus` เป็นค่าคงที่) (B) เปิด endpoint ใหม่ (C) ทำไม่ได้
- **สิ่งที่เราจะทำถ้ายังไม่ได้คำตอบ:** แบบ C — ให้ฝ่ายบัญชีกดปุ่ม "ลงบัญชีแล้ว" ใน TMS และถือว่าใบที่เก่ากว่าจำนวนวันที่ตกลงกันลงบัญชีแล้ว
- **ผลกระทบ:** A, B → TMS ล็อกการแก้อัตโนมัติเมื่อใบลงบัญชี / C → ต้องพึ่งการกดด้วยมือ มีความเสี่ยงแก้ทับใบที่ลงบัญชีแล้วโดยไม่รู้
- **คำตอบ:**

**KRS-8 — ถ้า TMS ส่ง `PUT` ทับใบที่ลง GL แล้ว KRS จะทำอย่างไร?**
- **บริบท:** เราต้องรู้เพื่อกำหนดว่า TMS ควรบล็อก เตือน หรือปล่อยผ่าน
- **ตัวเลือก:** (A) ปฏิเสธ — โปรดระบุรหัสตอบกลับ (B) รับ แต่ GL ไม่เปลี่ยน (เอกสารกับบัญชีไม่ตรงกัน) (C) รับ และกลับรายการ GL ให้อัตโนมัติ
- **สิ่งที่เราจะทำถ้ายังไม่ได้คำตอบ:** ถือว่าเป็น (B) ซึ่งเสี่ยงที่สุด — TMS บล็อก PUT ของใบที่ถูกระบุว่าลงบัญชีแล้ว จนกว่าฝ่ายบัญชีอนุมัติ
- **ผลกระทบ:** A → TMS จัดเป็นข้อผิดพลาดที่ต้องให้คนตัดสิน / B → ต้องบล็อกที่ฝั่ง TMS เสมอ / C → ปล่อยผ่านได้ ลดงานที่ทำด้วยมือ
- **คำตอบ:**

**KRS-9 — งวดบัญชีที่ปิดแล้ว: ถ้า TMS ส่งเอกสารใหม่ หรือแก้/ยกเลิกเอกสารที่ลงวันที่ในงวดที่ KRS ปิดแล้ว KRS จะตอบอย่างไร?**
- **บริบท:** เช่น วันที่ 10 ธ.ค. หลังปิดงวด พ.ย. แล้ว TMS ส่งใบแจ้งหนี้ลงวันที่ 28 พ.ย. หรือส่ง PUT แก้ใบของเดือน พ.ย.
- **ตัวเลือก:** (A) ปฏิเสธ พร้อมรหัสหรือข้อความเฉพาะ — โปรดระบุ (B) รับ แต่ลงในงวดปัจจุบัน (C) รับ และลงย้อนงวด — และมี API ให้ถาม "งวดที่ปิดล่าสุด" หรือไม่
- **สิ่งที่เราจะทำถ้ายังไม่ได้คำตอบ:** ถือว่าเป็น (A) — เอกสารใน TMS ออกและยกเลิกได้ตามปกติ ส่วนรายการที่ KRS ปฏิเสธเข้าคิว "ถูกปฏิเสธ" ให้ฝ่ายบัญชีตัดสิน (เช่น ออกใบลดหนี้ในงวดปัจจุบัน)
- **ผลกระทบ:** ถ้ามี API บอกงวดที่ปิด → TMS เตือนผู้ใช้ก่อนออกเอกสารย้อนงวด / ถ้าเป็น (B) → วันที่เอกสารสองระบบไม่ตรงกัน TMS ต้องเก็บ "วันที่ลงบัญชีฝั่ง KRS" แยก
- **คำตอบ:**

**KRS-10 — สถานะรับชำระ: TMS จะทราบได้อย่างไรว่าใบใดรับเงินแล้ว (เต็มจำนวน บางส่วน หรือถูกหัก ณ ที่จ่ายเท่าใด)?**
- **บริบท:** ถ้าฝ่ายบัญชีบันทึกรับเงินใน KRS TMS ต้องรู้เพื่อปิดยอดลูกหนี้ และถ้า TMS เป็นผู้ออกใบกำกับภาษี (ข้อ KRS-2 แบบ B) ต้องรู้วันรับเงินเพื่อออกใบกำกับภาษี
- **ตัวเลือก:** (A) เพิ่มฟิลด์ใน `GET /invoice` (B) endpoint ใหม่ เช่น `GET /invoice/{transactionNo}/payments` (C) KRS แจ้งกลับเมื่อมีการรับชำระ (webhook) (D) ไม่มี — บันทึกรับเงินใน TMS ด้วยมือ
- **สิ่งที่เราจะทำถ้ายังไม่ได้คำตอบ:** แบบ D — ฝ่ายบัญชีบันทึกรับชำระใน TMS เอง
- **ผลกระทบ:** A ถึง C → TMS ดึงสถานะมาเทียบยอดอัตโนมัติและแจ้งเมื่อไม่ตรง / D → ต้องบันทึกซ้ำสองระบบ และรายงานลูกหนี้ใน TMS อาจไม่ตรงกับ KRS
- **คำตอบ:**

### ค. ใบสั่งงาน (SO) และรหัสลูกค้า

**KRS-11 — ใบสั่งงาน (SO) จาก KRS: TMS จะอ่านได้ทางใด?**
- **บริบท:** เราสมมติว่า SO อยู่ในบริษัท NSF และ TMS จะอ่านทุก 5 นาที ข้อมูลที่ต้องใช้คือ เลข SO, วันที่, รหัสลูกค้า, ต้นทาง/ปลายทาง, รายการ, สถานะยกเลิก, เวลาแก้ไขล่าสุด
- **ตัวเลือก:** (A) KRS สร้าง view แบบอ่านอย่างเดียวในฐานข้อมูล พร้อมบัญชีเข้าใช้แยกที่มีสิทธิ์ SELECT เฉพาะ view นั้น (B) KRS เปิด API เช่น `GET /salesorder?since=` (C) ส่งไฟล์เป็นรอบ (D) ไม่ส่ง SO — สร้างงานใน TMS เอง
- **สิ่งที่เราจะทำถ้ายังไม่ได้คำตอบ:** แบบ D จนกว่าจะได้ช่องทาง — ผู้ใช้สร้างงานใน TMS เองหรือนำเข้าจาก Excel
- **ผลกระทบ:** A → เราต้องการชื่อ view และรายการคอลัมน์ที่ KRS รับรองว่าจะไม่เปลี่ยนโดยไม่แจ้ง / B → ไม่ต้องเปิดฐานข้อมูลให้ระบบภายนอก / C → ข้อมูลช้าตามรอบส่งไฟล์
- **คำตอบ:**

**KRS-12 — SO อยู่ในบริษัท NSF ส่วนใบแจ้งหนี้ออกในบริษัท PP ใช่หรือไม่ และรหัสลูกค้าของสองบริษัทเป็นรหัสเดียวกันหรือไม่?**
- **บริบท:** `custOrSuppCode` ในใบแจ้งหนี้ต้องเป็นรหัสที่มีใน KRS ถ้ารหัสลูกค้าใน SO (NSF) ต่างจากรหัสใน PP TMS ต้องเก็บสองรหัสต่อลูกค้าหนึ่งราย เราสมมติด้วยว่า 1 ใบแจ้งหนี้ = 1 ลูกค้า และรวมได้หลาย SO/DO
- **ตัวเลือก:** (A) รหัสเดียวกันทั้งสองบริษัท (B) คนละรหัส — KRS มีตารางจับคู่ให้ (C) คนละรหัส — ไม่มีตารางจับคู่ ต้องจับคู่ด้วยมือใน TMS
- **สิ่งที่เราจะทำถ้ายังไม่ได้คำตอบ:** แบบ C — TMS เก็บรหัสแยกต่อบริษัท และให้ผู้ใช้จับคู่ครั้งแรกที่พบลูกค้าใหม่ (งานของลูกค้านั้นจะค้างจนกว่าจะจับคู่)
- **ผลกระทบ:** A → จับคู่ครั้งเดียว / B → TMS ดึงตารางจับคู่อัตโนมัติ / C → มีงานที่ทำด้วยมือทุกครั้งที่มีลูกค้าใหม่
- **คำตอบ:**

## ส่วนที่ 2 — ตอบก่อนเปิดใช้จริง

**KRS-13 — เมื่อฝ่ายบัญชีเปิดใบที่มาจาก API แล้วกดบันทึก รายการถูกเขียนใหม่ และบางรายการหรือบางฟิลด์หาย — แก้ที่ต้นเหตุได้หรือไม่?**
- **บริบท:** เคยเกิดจริง ใบ 79 รายการ ยอด 2,054,000 บาท หลังกดบันทึกเหลือ 30 รายการ ยอด 780,000 บาท และฟิลด์รถ/เส้นทาง (`carId`, `carPerson`, `frWay`, `toWay`) ว่าง
- **ตัวเลือก:** (A) แก้โปรแกรมหรือตั้งค่าให้ไม่เขียนทับรายการและไม่ล้างฟิลด์ — ภายในเมื่อใด (B) แก้ไม่ได้ — มีวิธีใช้งานที่เลี่ยงได้ (โปรดระบุ) (C) ยังไม่ทราบสาเหตุ — ขอข้อมูลว่าฟิลด์รถ/เส้นทางอยู่ตารางเดียวกับรายการหรืออยู่ตารางลูก
- **สิ่งที่เราจะทำถ้ายังไม่ได้คำตอบ:** TMS ดึงใบกลับมาเทียบทันทีหลังส่ง และเทียบซ้ำเป็นรอบ ถ้ายอดเงินไม่ตรงจะแจ้งเตือนระดับสูงสุดทันที
- **ผลกระทบ:** A → ลดการเทียบซ้ำและงานแก้ด้วยมือ / B, C → ต้องคงการเทียบทุกรอบ และฝ่ายบัญชีต้องแก้ใบที่ผิดด้วยมือ
- **คำตอบ:**

**KRS-14 — ขอ endpoint ค้นใบด้วยเลขของ TMS (เช่น `GET /invoice?tmsVoucherNo=`)**
- **บริบท:** เมื่อ `POST` สำเร็จแต่คำตอบหายระหว่างทาง การส่งซ้ำจะได้ 409 (เลขซ้ำ) ซึ่งไม่บอก `transactionNo` TMS จึงไม่รู้ว่าใบที่สร้างแล้วคือเลขใด
- **ตัวเลือก:** (A) เปิด endpoint ค้นด้วย `tmsVoucherNo` (B) ให้คำตอบ 409 แนบ `transactionNo` ของใบที่ซ้ำมาด้วย (C) ทำไม่ได้
- **สิ่งที่เราจะทำถ้ายังไม่ได้คำตอบ:** แบบ C — รายการเข้าคิวให้คนเปิด KRS หา `transactionNo` แล้วกรอกใน TMS ด้วยมือ
- **ผลกระทบ:** A, B → กู้คืนได้อัตโนมัติ ไม่ต้องใช้คน
- **คำตอบ:**

**KRS-15 — รหัสหลักที่ KRS ยอมรับ: ขอรายการ (หรือ endpoint) ของค่าที่ใช้ได้สำหรับ `mainUnits`, `salePerson`/`saleName`, `entryBy`, `itemCode`, `accountCode` และรหัสลูกค้า**
- **บริบท:** ค่าที่ไม่มีใน KRS ทำให้ได้ 400 TMS จึงต้องตรวจก่อนส่ง เช่น หน่วย "เที่ยว/ตัน/กม." ต้องสะกดตรงกับข้อมูลหลักของ KRS และเราไม่แน่ใจว่า `entryBy` ต้องเป็นผู้ใช้ที่มีใน ERP หรือใช้ค่าคงที่ "TMS" ได้
- **ตัวเลือก:** (A) เปิด endpoint อ่านข้อมูลหลัก ให้ TMS ดึงเป็นรอบ (B) ส่งรายการเป็นไฟล์ และแจ้งเมื่อมีการเปลี่ยน (C) อื่น ๆ
- **สิ่งที่เราจะทำถ้ายังไม่ได้คำตอบ:** แบบ B — นำเข้ารายการครั้งเดียว และให้ผู้ดูแลแก้ใน TMS เองเมื่อ KRS เปลี่ยน
- **ผลกระทบ:** A → TMS ตรวจได้ตรงเสมอ / B → เสี่ยงข้อมูลไม่ตรงเมื่อ KRS เพิ่มหรือเปลี่ยนรหัส (เอกสารจะถูกปฏิเสธจนกว่าจะแก้)
- **คำตอบ:** ช่องทาง ___ / `entryBy` ใช้ค่า ___ / `accountCode` เริ่มต้น ___

**KRS-16 — ใบส่งของ (DO): ต้องการให้ DO เข้าไปเก็บใน KRS เป็นเอกสารแยกหรือไม่?**
- **บริบท:** ปัจจุบันไม่มี endpoint DO เลขและวันที่ DO ปรากฏในรายการของใบแจ้งหนี้ผ่าน `flowNo` และ `flowDate`
- **ตัวเลือก:** (A) ไม่ต้อง — ปรากฏใน `flowNo`/`flowDate` ก็เพียงพอ (B) ต้องการ — KRS จะเปิด `POST /deliveryorder` (โปรดระบุประเภทเอกสารใน KRS และกำหนดการ)
- **สิ่งที่เราจะทำถ้ายังไม่ได้คำตอบ:** แบบ A
- **ผลกระทบ:** B → เพิ่มการส่ง DO เมื่อส่งของเสร็จ และการอ้างอิง DO กับใบแจ้งหนี้ฝั่ง KRS
- **คำตอบ:**

**KRS-17 — SO ที่ถูกแก้หรือยกเลิกใน KRS หลังจาก TMS วางแผนรถไปแล้ว — KRS แจ้ง TMS ได้หรือไม่?**
- **บริบท:** เช่น SO ถูกเปลี่ยนปลายทางหลังจัดรถแล้ว TMS จะไม่เขียนทับแผนอัตโนมัติ แต่จะแจ้งผู้วางแผนพร้อมแสดงส่วนที่ต่าง
- **ตัวเลือก:** (A) KRS แจ้งกลับเมื่อ SO เปลี่ยนหรือยกเลิก (webhook หรือ API) (B) ไม่แจ้ง — TMS ตรวจเองจากเวลาแก้ไขล่าสุดและสถานะยกเลิก — โปรดยืนยันว่าทุกการแก้ไขและยกเลิกทำให้สองคอลัมน์นี้เปลี่ยนเสมอ
- **สิ่งที่เราจะทำถ้ายังไม่ได้คำตอบ:** แบบ B
- **ผลกระทบ:** B → เห็นการเปลี่ยนแปลงช้าได้ถึงรอบการอ่าน (5 นาที) และถ้าคอลัมน์ไม่เปลี่ยนทุกกรณี TMS จะพลาดการแก้ไขบางรายการ
- **คำตอบ:**

**KRS-18 — ข้อตกลงการใช้งาน API: ระบบทดสอบ ขีดจำกัดการเรียก ช่วงปิดปรับปรุง และผู้ติดต่อเมื่อระบบขัดข้อง**
- **บริบท:** TMS ตั้งใจส่งพร้อมกันไม่เกิน 3 คำขอ ตั้งเวลารอ 120 วินาที (ใบใหญ่เคยมี 446 รายการ) และเทียบยอดช่วงกลางคืน
- **ตัวเลือก:** โปรดระบุ — (1) มี API และฐานข้อมูลทดสอบแยกจากระบบจริงหรือไม่ ถ้าไม่มีจะทดสอบ POST/PUT อย่างไร (2) จำนวนคำขอต่อนาทีที่รับได้ และ timeout ฝั่ง server (3) ช่วงเวลาปิดปรับปรุงหรือสำรองข้อมูลประจำ (4) ผู้ติดต่อและเวลาตอบกลับเมื่อ API ล่ม (503) ในช่วงนำร่อง
- **สิ่งที่เราจะทำถ้ายังไม่ได้คำตอบ:** ส่งพร้อมกัน 3 คำขอ ลองใหม่เมื่อได้ 503 ที่ 1/2/5/15/30/60 นาที และทดสอบกับระบบจริงด้วยเอกสารทดสอบที่ตกลงกัน
- **ผลกระทบ:** กำหนดค่าการส่งและการลองใหม่ เวลาของงานเทียบยอดกลางคืน และขั้นตอนทดสอบก่อนเปิดใช้จริง
