# ขั้นตอนรับมือและแจ้งเหตุละเมิดข้อมูลส่วนบุคคล (ภายใน 72 ชั่วโมง)

> **ร่าง — ยังไม่ผ่านการตรวจของทนาย ห้ามใช้จริงก่อนตรวจ**
>
> ฉบับร่าง 1 · 20 พ.ย. 2569 (ST9-T16) · ใช้กับทีม Innovera และแนบให้ tenant นำร่องเพื่อรู้ว่าจะได้รับแจ้งอะไร เมื่อไร

## 1. หลักที่ใช้

| เรื่อง | ข้อกำหนด | ที่มา |
|---|---|---|
| ผู้ควบคุมแจ้ง สคส. | โดยไม่ชักช้าภายใน 72 ชั่วโมงนับแต่ทราบเหตุ เว้นแต่เหตุนั้นไม่มีความเสี่ยงที่จะกระทบสิทธิเสรีภาพของบุคคล | พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 มาตรา 37(4) |
| ผู้ควบคุมแจ้งเจ้าของข้อมูล | เมื่อเหตุมีความเสี่ยงสูงที่จะกระทบสิทธิเสรีภาพ ให้แจ้งเจ้าของข้อมูลพร้อมแนวทางเยียวยาโดยไม่ชักช้า | มาตรา 37(4) |
| ผู้ประมวลผลแจ้งผู้ควบคุม | ผู้ประมวลผลต้องแจ้งเหตุละเมิดที่เกิดขึ้นแก่ผู้ควบคุม | มาตรา 40 — **[ต้องให้ทนายตรวจ: กรอบเวลาและรายละเอียดตามประกาศคณะกรรมการฯ เรื่องหลักเกณฑ์การแจ้งเหตุ]** |
| Innovera → tenant | ไม่เกิน **24 ชั่วโมงหลังยืนยันเหตุ** | NFR-307 [PROPOSED], DPA ข้อ 8.1 |
| ข้อมูลที่ Innovera เป็นผู้ควบคุม (บัญชีผู้ใช้, log ความปลอดภัย — RoPA ส่วนที่ 2) | Innovera แจ้ง สคส. เองภายใน 72 ชั่วโมง | NFR-307 |
| เหตุรั่วข้าม tenant | Sev-1: หยุด deploy, แจ้ง tenant ที่กระทบภายใน 24 ชม., ประเมินแจ้ง สคส. ภายใน 72 ชม. | NFR-209 |

**[ต้องให้ทนายตรวจ]**: (ก) "ทราบเหตุ" ของ tenant เริ่มนับเมื่อใด เมื่อเหตุเกิดที่ Innovera (ข) รูปแบบ/ช่องทางการแจ้ง สคส. และรายการข้อมูลที่ต้องมี (ค) เกณฑ์ "ความเสี่ยง" และ "ความเสี่ยงสูง" (ง) ต้องเก็บบันทึกเหตุที่ไม่ได้แจ้งหรือไม่ และนานเท่าใด (จ) การแจ้งหน่วยงานอื่น เช่น ตำรวจ/หน่วยงานไซเบอร์

## 3. ระดับเหตุ (เสนอ)

| ระดับ | ตัวอย่าง | เป้าเวลา |
|---|---|---|
| Sev-1 | ข้อมูลรั่วข้าม tenant; ฐานข้อมูล/backup หลุด; key เข้ารหัส (`FIELD_ENCRYPTION_KEYS`) หรือ `BLIND_INDEX_KEY` หลุด; ผู้ไม่มีสิทธิ์ถอดเลขบัตร/บัญชีได้ | เริ่มดำเนินการทันที; แจ้ง tenant ≤ 24 ชม. หลังยืนยัน |
| Sev-2 | บัญชีผู้ใช้ tenant ถูกยึด; ลิงก์รถร่วม/ผู้รับหลุดและถูกใช้; ไฟล์ POD/ไฟล์นำเข้าถูกดาวน์โหลดโดยมิชอบ; ส่ง SMS/อีเมลผิดคน | ≤ 4 ชม. เริ่มสืบสวน; แจ้ง tenant ≤ 24 ชม. หลังยืนยัน |
| Sev-3 | ข้อมูลบุคคลหลุดลง log ภายในโดยไม่มีผู้เข้าถึงภายนอก; เหตุที่ประเมินแล้วไม่มีความเสี่ยง | ภายใน 3 วันทำการ; บันทึกในทะเบียนเหตุ |

## 4. ไทม์ไลน์ (T0 = เวลาที่ Innovera ทราบเหตุ)

| เวลา | ขั้น | ทำอะไร |
|---|---|---|
| T0 | รับแจ้ง/ตรวจพบ | ช่องทาง: alert จาก monitoring (ST9-T19), รายงานจากลูกค้า/พนักงาน, {{อีเมล security@…}} · เปิดบันทึกเหตุ (ข้อ 7) ทันที บันทึกเวลา T0 |
| ≤ T0 + 1 ชม. | คัดแยก | Incident lead ตัดสินระดับเหตุ (ข้อ 3) และว่าเกี่ยวข้อมูลส่วนบุคคลหรือไม่ |
| ทันที (คู่ขนาน) | ระงับ | ดูข้อ 5 |
| ≤ T0 + 24 ชม. | ยืนยันเหตุ + แจ้ง tenant | ระบุ tenant ที่กระทบ, ประเภทข้อมูล, จำนวนโดยประมาณ → แจ้งตามแบบข้อ 6.1 (แจ้งได้แม้ข้อมูลยังไม่ครบ แล้วส่งเพิ่ม) |
| ≤ 72 ชม. นับแต่ tenant ทราบเหตุ | tenant แจ้ง สคส. | Innovera ส่งข้อมูลประกอบตามที่ tenant ขอ (ร่างข้อ 6.2) |
| ≤ 72 ชม. นับแต่ T0 | Innovera แจ้ง สคส. (เฉพาะข้อมูลที่ Innovera เป็นผู้ควบคุม) | ร่างข้อ 6.2 ผ่านที่ปรึกษากฎหมาย |
| เมื่อความเสี่ยงสูง | แจ้งเจ้าของข้อมูล | ผู้ควบคุมเป็นผู้แจ้ง (tenant สำหรับข้อมูลของ tenant) — Innovera ช่วยร่างข้อความ |
| ≤ 14 วันหลังปิดเหตุ | ทบทวนหลังเหตุ | หาสาเหตุราก, มาตรการกันซ้ำ, อัปเดต RoPA/DPA ถ้าเปลี่ยน |

## 5. การระงับและเก็บหลักฐาน — เครื่องมือที่มีในระบบ

| สถานการณ์ | วิธีระงับ (มีในโค้ดแล้ว) |
|---|---|
| บัญชีผู้ใช้ถูกยึด | ปิดใช้งานผู้ใช้ / เพิ่ม `token_version` ทำให้ token ทุกตัวใช้ไม่ได้ (`app_user.token_version`), เพิกถอน trusted device, บังคับรีเซ็ตรหัสผ่าน |
| API key / OAuth client หลุด | เพิกถอน API key (ST7) — ลง audit |
| ลิงก์รถร่วม/ผู้รับหลุด | เพิกถอน magic link (`magic_link.revoked_at` + เหตุผล) |
| Credential connector / token LINE หลุด | หมุน credential ที่ระบบปลายทาง แล้วตั้งใหม่ (`PUT /connectors/:id/credentials`, `PATCH /v1/settings/messaging`) |
| Key เข้ารหัสฟิลด์หลุด | เพิ่ม key ใหม่หน้า key ring (`FIELD_ENCRYPTION_KEYS="k2:…,k1:…"`) แล้วเข้ารหัสค่าเดิมใหม่ (`needsRotation` — `common/crypto.ts`) **[ยังไม่มี runbook/สคริปต์เข้ารหัสใหม่ทั้งฐาน — ต้องทำ]** |
| รั่วข้าม tenant | หยุด deploy, rollback, ปิดฟีเจอร์ที่เกี่ยว (NFR-209) |
| พนักงาน Innovera ใช้สิทธิ์มิชอบ | ปิด `platform_user`, ตรวจ `impersonation_session` |

**หลักฐานที่ต้องเก็บก่อนแก้ไข:** export `audit_log` ช่วงเวลาที่เกี่ยว (รวม `driver.pii_revealed`, `carrier.pii_revealed`, การกระทำระหว่างเข้าดูแทน), `login_attempt` (อีเมล/IP/user agent), `impersonation_session`, log แอป (ตัด secret แล้ว), log ของผู้ให้บริการ cloud **[OPEN ST0-T01]** · อย่าลบหรือแก้ log เดิม · ระวัง: งาน retention ลบ `login_attempt` > 12 เดือนและ GPS > 90 วันทุกวัน — ถ้าเหตุเกี่ยวข้อง ให้ export ก่อน **[ยังไม่มีสวิตช์ระงับงาน retention ระหว่างสอบสวน (legal hold) — ต้องทำ]**

```
3. ประเภทข้อมูลและเจ้าของข้อมูลที่อาจกระทบ (อ้างรหัสกิจกรรมใน RoPA เช่น P-01 คนขับ): {{ }}

8. สิ่งที่แนะนำให้ tenant ทำ (เช่น แจ้ง สคส. ภายใน 72 ชม. นับแต่ทราบเหตุ, แจ้งคนขับ): {{ }}
9. ผู้ติดต่อของ Innovera: {{ชื่อ เบอร์ อีเมล}}
10. รอบรายงานถัดไป: {{ }}
```

### 6.2 ข้อมูลประกอบการแจ้ง สคส.

ใช้หัวข้อเดียวกับ 6.1 ข้อ 1–7 และเพิ่มชื่อ/ช่องทางติดต่อผู้ควบคุมและ DPO — **[ต้องให้ทนายตรวจ: แบบฟอร์มและช่องทางที่ สคส. กำหนดจริง]**

### 6.3 ข้อความถึงเจ้าของข้อมูล (เมื่อความเสี่ยงสูง)

ส่งในนามผู้ควบคุม: เกิดอะไรขึ้น, ข้อมูลอะไรของท่าน, ท่านควรทำอะไร (เช่น ระวังการแอบอ้าง/เปลี่ยนรหัสผ่าน), สิ่งที่บริษัททำแล้ว, ช่องทางติดต่อ — **[ต้องให้ทนายตรวจ]**

## 7. ทะเบียนเหตุ

ทุกเหตุ (รวมที่ไม่ต้องแจ้ง) บันทึก: เลขเหตุ, T0, ผู้รายงาน, ระดับ, tenant ที่กระทบ, ข้อมูลที่กระทบ, การประเมินความเสี่ยง + เหตุผลถ้าไม่แจ้ง, เวลาแจ้ง tenant/สคส./เจ้าของข้อมูล, การระงับ, สาเหตุราก, มาตรการกันซ้ำ · เก็บที่ {{ระบบ ticket — ห้ามใส่ข้อมูลส่วนบุคคลของผู้เสียหายเกินจำเป็น}} · หัวข้อ "Defect / Incident" ใน PROGRESS.md ใช้บันทึกสรุปแบบไม่มีข้อมูลบุคคลเท่านั้น
