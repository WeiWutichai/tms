### 2.1 ข้อมูลตั้งต้น (`seed.ts`) — ผลเท่าเดิมทุกครั้ง (ไม่มีค่าสุ่ม)

1. สร้างฐานใหม่ → `db:migrate` (ทางเดียวกับทุกที่) → tenant ผ่าน `createTenantWithDefaults`
2. **ผ่าน API จริง (role แอป + RLS):** ลูกค้า 46 ราย, จุดรับ-ส่ง, rate card (อนุมัติ), รถ + คนขับ 200 ชุด (plan/03 "กระดาน 200 คัน"), งานตัวอย่าง 2 ใบเต็มวงจร
   (ใบสั่ง → DO → เที่ยว → assign/dispatch → ถึง/ส่งสำเร็จ → ส่งบัญชี) และร่าง → ออกใบแจ้งหนี้จริง 1 ใบ (รวม render PDF)
3. **ขยายด้วย bulk insert (connection เจ้าของฐาน):** clone แถวตัวอย่างด้วย `jsonb_populate_record` — id ใหม่ = `md5(id ตัวอย่าง + ลำดับ)`

   (trigger ของเอกสารไม่ยอมให้เขียนใบที่ออกแล้วตรง ๆ) · จบด้วย `ANALYZE`

  เกิน `--abort-load` (12) = ทิ้งผลของส่วนนั้นแล้วรอเครื่องว่างวัดใหม่ (≤ 3 ครั้ง; finalize/run ที่ใช้ข้อมูลหมดไปติดป้ายแทน) ·

- **หา query ช้า:** seed ตั้ง `log_min_duration_statement = 150` เฉพาะฐาน perf → อ่านจาก `docker logs tms-postgres` แล้ว
  `EXPLAIN (ANALYZE, BUFFERS)` ด้วย role `tms_app` + `set_config('app.tenant_id', …)` (ผ่าน RLS เหมือนแอป)
- **รันซ้ำ:** `finalize` และ `run` ใช้ข้อมูลหมดไป (สคริปต์จำไว้ใน `state.json` และปฏิเสธรันซ้ำ) → รันใหม่ = `perf all`

### 4.1 คิวพร้อมวางบิล p95 610 ms บนคิว 5,500 DO — **แก้แล้วใน PR นี้** (ticket P-3)

**FACT (EXPLAIN ANALYZE บนฐาน perf, role `tms_app` + RLS, ก่อนแก้):** ต่อคำขอมี 2 query + ตรวจหลักฐานต่อแถว

   ประเมิน `delivery_order` เหลือ **1 แถว** (จริง 5,951) → nested loop + seq scan ลูกค้าต่อ DO (`Rows Removed by Join Filter: 118,558`)
   · query ยอดรวม 194 ms
3. `pod.checkCurrent` ทีละแถว = ~100 query ต่อหน้า 50 แถว

**แก้ (ผลลัพธ์/ลำดับเท่าเดิม · ไม่มี migration):** `apps/api/src/modules/invoices/billing-queue.service.ts`
- เทียบสถานะเป็น enum (`::do_status[]`, `::billing_status[]`) — ประเมินได้ 4,076 แถว (จริง 5,951) planner เลือก join ที่ถูก
