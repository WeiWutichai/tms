# TMS Functional & Platform Requirements

Oct 14, 2026 · @wei

ระบบมี 9 โมดูล รวม 120+ ฟังก์ชัน แบ่งเป็น **P0** (ต้องมีก่อนขึ้น KRS pilot) **P1** (ก่อนเปิดขาย standalone) **P2** (เฟสขยาย) เอกสารนี้เป็น checklist ฟังก์ชันที่ครบทั้งระบบ ส่วนวิธีทำงานภายในของ flow KRS อยู่ในเอกสาร "TMS × KRS Integration" และเรื่องราคา/tenant อยู่ใน "Product & Commercial"

## A. Platform, Authentication และสิทธิ์

**A1. Authentication**

|------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----|

กฎเพิ่มเติม: ผู้สร้าง Invoice อนุมัติใบตัวเองไม่ได้ (separation of duties, ปิดได้สำหรับ tenant เล็กโดย owner ยอมรับความเสี่ยง); ทุกการเปลี่ยน role ต้อง 2FA ซ้ำ (step-up)

**A4. Innovera platform admin** — role `super_admin`, `support` (อ่านอย่างเดียว + impersonate แบบมี audit และแจ้ง tenant owner ทางอีเมลทุกครั้ง), `billing`; ทุกคนบังคับ 2FA + IP allowlist (P1)

**A5. Audit log (ระดับระบบ)** — ทุก create/update/delete ของทุก entity: ใคร อะไร ค่าเก่า→ใหม่ (diff jsonb) เวลา IP เหตุผล (ถ้าเป็น override); อ่านได้จากหน้า entity นั้นและหน้า audit รวม; เก็บ 5 ปี (ตามอายุความเอกสารบัญชี); append-only ไม่มีสิทธิ์ลบ — P0

## B. Master data

ทุก master มี: ค้นหา/กรอง, สร้าง/แก้/ปิดใช้ (ไม่ลบถ้ามีเอกสารอ้างถึง), import CSV พร้อม preview และรายงานแถวที่ผิด, export, ประวัติการแก้ — P0 ทั้งหมดเว้นที่ระบุ

| Master                | ฟิลด์หลัก                                                                                                                                                        | ฟังก์ชันเฉพาะ                                                            |
|-----------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------|
| ลูกค้า / คู่ค้า            | ชื่อ, เลขผู้เสียภาษี, สาขา, ที่อยู่ออกใบกำกับ, ที่อยู่ส่ง (หลายจุด), ผู้ติดต่อ, เครดิตวัน, พนักงานขาย, รหัสฝั่ง ERP (หลาย ERP ได้), รอบวางบิล                                              | map รหัส NSF↔PP; ตรวจเลขผู้เสียภาษี 13 หลัก; รวมลูกค้าซ้ำ (merge) P1           |
| จุดส่ง / สถานที่          | ชื่อ, ที่อยู่, พิกัด (ปักบนแผนที่หรือ geocode), เวลาเปิด-ปิด, ประเภทรถที่เข้าได้, เวลาจอดเฉลี่ย, ผู้ติดต่อ, หมายเหตุหน้างาน                                                             | geocode อัตโนมัติ + ให้คนยืนยัน; จุดที่ geocode ไม่ได้ขึ้นรายการรอ                 |
| เส้นทาง (route)        | ต้นทาง, ปลายทาง, ระยะทาง, เวลามาตรฐาน, ทางด่วน/ค่าผ่านทาง, ประเภทรถ                                                                                               | route = คู่ต้นทาง-ปลายทางที่ใช้จับคู่ SO อัตโนมัติ; ระยะทางจาก map API หรือกรอก    |
| รถ                    | ทะเบียน, จังหวัด, ประเภท (กระบะ/6 ล้อ/10 ล้อ/พ่วง/ห้องเย็น), น้ำหนักบรรทุก, ปริมาตร, เจ้าของ (บริษัท/ผู้รับเหมา), วันหมดประกัน/ภาษี/พรบ., กล่อง GPS (ค่าย+รหัส), สถานะ (พร้อม/ซ่อม/ปลด) | แจ้งเตือนเอกสารรถใกล้หมดอายุ 30 วัน; นับรถ active สำหรับ tier                |
| คนขับ                  | ชื่อ, เบอร์, เลขใบขับขี่ + ประเภท + วันหมดอายุ, สังกัด (บริษัท/ผู้รับเหมา), รถประจำ, สถานะ                                                                                   | ตรวจประเภทใบขับขี่ตรงกับประเภทรถตอนจ่ายงาน (DLT); แจ้งเตือนใบขับขี่หมดอายุ       |
| ผู้รับเหมา / รถร่วม       | ชื่อ, เลขผู้เสียภาษี, ผู้ติดต่อ, เงื่อนไขจ่าย, rate card ขาซื้อ, รถและคนขับในสังกัด, คะแนนประเมิน                                                                                | ประเมินประสิทธิภาพ (ตรงเวลา, ตีกลับ, ร้องเรียน) P1                           |
| Rate card (ขาขาย)     | ต่อลูกค้า: ราคาต่อเที่ยว/ตัน/กม./ชิ้น ตามเส้นทาง × ประเภทรถ, ค่าใช้จ่ายเพิ่ม (รอคิว, ค้างคืน, ยกของ), มีผลตั้งแต่-ถึง                                                                | ราคาถูก snapshot ลง DO ณ วันส่ง; ราคาซ้อนช่วงเวลาไม่ได้                      |
| Rate card (ขาซื้อ)      | ต่อผู้รับเหมา โครงเดียวกับขาขาย                                                                                                                                     | ใช้คำนวณต้นทุนเที่ยวและใบจ่ายรถร่วม P1                                       |
| สินค้า / หน่วย           | รหัส, ชื่อ, หน่วย, น้ำหนัก/ปริมาตรต่อหน่วย, อุณหภูมิ (ถ้าห้องเย็น), สินค้าอันตราย                                                                                               | ใช้คำนวณ load และ compatibility; map กับ `itemCode`/`mainUnits` ของ ERP |
| คลัง / สาขา (ต้นทาง)    | ชื่อ, ที่อยู่, พิกัด, ช่องโหลด, เวลาทำการ, time slot                                                                                                                   | time slot management P2                                               |
| รหัส ERP (master code) | ค่าที่ ERP ยอมรับ: หน่วย, พนักงานขาย, บัญชี, สินค้า ต่อ connector                                                                                                        | ใช้ validate ก่อนส่ง (กัน 400)                                            |

## C–E. TMS core: รับงาน → วางแผน → จ่ายงาน → ส่ง → POD

**C. Order intake**

|------------------------------|--------------------------------------------------------------------------------------------------------|-----|
| รับ SO จาก ERP                | ผ่าน ERP adapter (KRS: SQL read-only poller) ทุกใบเข้าระบบเสมอ                                            | P0  |
| กรอก SO มือ / import CSV      | สำหรับ standalone หรือลูกค้าที่ไม่มีใน ERP; template CSV + ตรวจแถวผิด                                           | P0  |
| รับงานจากลูกค้าผ่าน portal / API | ลูกค้าของ tenant สั่งงานเอง (customer portal)                                                              | P2  |
| จับคู่อัตโนมัติ                    | ลูกค้า (รหัส ERP → customer), ต้นทาง/ปลายทาง (ข้อความ → จุดส่ง/route ด้วย alias + fuzzy match)                 | P0  |
| หน้าใบค้าง                     | `ROUTE_PENDING`, `CUSTOMER_UNMAPPED`, `SOURCE_ERROR`, SO ที่ ERP แก้หลังวางแผน — พร้อมเหตุผลและ action เคลียร์ | P0  |
| เรียนรู้ alias                  | เมื่อคน map ข้อความ "โรงงานบางปู" → จุดส่ง X ให้จำเป็น alias ครั้งต่อไปจับอัตโนมัติ                                   | P0  |
| แยก / รวม SO                 | แยก SO เป็นหลายเที่ยว, รวมหลาย SO ลูกค้าเดียวในเที่ยวเดียว (ออกหลาย DO)                                         | P0  |
| ยกเลิก / คืนสถานะ              | พร้อมเหตุผล; SO ที่มี DO แล้วห้ามยกเลิกตรง ต้องยกเลิก DO ก่อน                                                     | P0  |

| จัดเที่ยวหลายจุด (multi-drop)     | เรียงลำดับจุดส่งด้วยมือ, คำนวณระยะ/เวลารวมจาก route master                                                            | P0  |

| จ่ายงานผู้รับเหมา                 | ส่งงานให้รถร่วมพร้อมราคาซื้อ, รับ/ปฏิเสธผ่าน LINE/อีเมล/portal ภายในเวลา, หมดเวลา → จ่ายรายถัดไป                            | P1  |
| ตารางรถ / คนขับรายวัน           | ดูภาระงาน ว่าง ซ่อม ลา                                                                                             | P0  |
| ใบงานประจำวัน                  | พิมพ์/ส่ง LINE ใบสั่งงานให้คนขับ (ก่อนมี Driver app)                                                                     | P0  |
| งานประจำ (recurring)          | SO ที่วิ่งทุกวัน/สัปดาห์ สร้างล่วงหน้าอัตโนมัติ                                                                               | P1  |

**E. Execution & POD**

| ฟังก์ชัน                            | รายละเอียด                                                                  | P        |
|----------------------------------|----------------------------------------------------------------------------|----------|
| ออก DO                           | จาก SO ที่ PLANNED: 1 DO = 1 เที่ยว, snapshot รถ คนขับ ต้นทาง ปลายทาง น้ำหนัก ราคา | P0       |
